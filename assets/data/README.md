# `assets/data/` — vendored wordlist and certificate data

Static data served to the browser (and read from disk in Node). The wordlists are loaded by
`assets/js/lib/wordlist.js` (`loadWordlist`) and **generated by `tools/build-wordlists.mjs`** —
do not edit them by hand; re-run the builder and update the embedded counts in `wordlist.js`
(a unit test enforces they match). Three exceptions:

- `sample-cert.pem`, the certificate behind "Try a sample" in the Certificate and SSL Targets
  views: a leaf for `example.com` / `example.net` and its intermediate, issued by a made-up
  "DomainScope Sample" CA whose keys were never saved. `tests/fixtures/gen_x509_fixtures.mjs`
  crafts it (when missing, or with `--force`).
- `intermediates/`, the public TLS intermediate certificates and root store data of the Common
  CA Database (CCADB), generated by `tools/build-intermediates.mjs` (see
  [below](#intermediates--the-ccadb-intermediate-list)).
- `ctlogs.json`, a compact copy of Google's CT log list v3 (the logs Chrome recognises, their
  operators, states and shards), the fallback of Certificate › Transparency when the page cannot
  fetch the live list; generated by `tools/build-ctlogs.mjs` (one log a line).
- `senders/`, the reverse-DNS lists behind DMARC & TLS reports › Identify senders, generated by
  `tools/build-senders.mjs` from parsedmarc's map (see
  [below](#senders--the-sender-lists-of-dmarc--tls-reports)).

The product is **global**: these lists are generic (English/tech/DevOps first),
never tuned to any single organisation's DNS zone.

In the UI the levels are **Small** (the 159-label core built into `wordlist.js`, no file), **Smart** (default), **Large** and **Huge**; each scanned domain gets its own list, ordered custom wordlist → learned names → small core → locale packs → tier. A user's custom wordlist and learned names never live here: they stay in the viewer's browser (session / local storage).
The tiers are **strict prefixes of one master ranking**, so
base ⊂ large ⊂ huge and `loadWordlist` can extend one from the next. The `.gz`
files are decoded with `DecompressionStream('gzip')` in the browser and
`node:zlib` in Node; if GitHub Pages serves a `.gz` already decompressed, the
loader detects the missing gzip magic bytes and reads it as text. All three tier
files are self-hosted — no runtime dependency on `raw.githubusercontent.com`.

## Ranking

`tools/build-wordlists.mjs` normalises every source label (lowercase; single
DNS label `[a-z0-9-]`, ≤63, no leading/trailing `-`; drops dotted/underscored
fragments, over-long tokens, hex/uuid hashes and numeric-only labels beyond
small numbers), then ranks by reciprocal-rank fusion across the sources. The
SecLists top-1M list (Cloudflare-derived real usage) is the primary signal;
labels present in several popular lists rank higher; the hand-curated core
(`WORDLIST_SMALL`/`MEDIUM`) leads the smart base. Quality guards: a label seen in
**only** bitquark (whose passive-DNS data carries wildcard-spam zones) is dropped
for lack of corroboration; flat vocabularies (dnsgen/altdns/services-names) only
break ties for labels a ranked source already has, never pulling an arbitrary
word in on their own; and a content filter drops Chinese gambling/SEO spam,
keyboard-mash strings, `cf-protected*` and adult/profanity/slur/pharma labels
(generic business labels like `casino`/`bet`/`sex`/`xxx` are kept — they are real
subdomains on those operators' own zones).

## `locale/<cc>.txt`

Curated per-market packs (`tr, de, fr, es, pt, it, nl, pl, ru, ar, ja, zh`),
ASCII-folded (transliterated where the language is non-Latin). Each is generic
business / public-service / e-commerce / accounting / e-invoicing / e-government
/ education / healthcare / logistics / HR vocabulary for that market — **curated
from general domain knowledge, never from any single company's zone**. Source of
truth is `tools/locale-data.mjs`. Scans pass each scanned domain to `loadWordlist`, so packs are picked
automatically from its TLD, the last label (e.g. `.com.tr`→`tr`, `.de`/`.at`→`de`,
`.ch`→`de`+`fr`+`it`); a TLD without packs of its own — `.com`, or a country
ending with no pack such as `.co.uk` — gets them from the scan's evidence instead
(the words of the names found, the countries of its name and mail servers;
adaptive locale packs, `docs/SPEC.md` §5.89), unless the user chooses packs — or
none — under Subdomains › Advanced options (the scanner's `locales` option). Packs apply from the Smart level up; the full mapping is in
`docs/SPEC.md` §5.6. (MIT, original DomainScope curation.)

All plain-text files are UTF-8, one label per line, LF endings. `loadWordlist`
validates every label and skips blank / `#`-comment lines.

## `intermediates/` — the CCADB intermediate list

The Certificate view (and SSL Targets step 1) completes a chain that stops short of a root: a
server certificate uploaded without its intermediate is the most common installation error, and
the browser cannot fetch the certificate's AIA `caIssuers` URL (plain `http://`, no CORS).
`assets/js/lib/chainfix.js` looks the missing issuer up here instead and offers `fullchain.pem`;
it also warns when the chain ends at a root a store distrusts, removed or lets expire first.
**Generated by `tools/build-intermediates.mjs`** (maintainers, and the weekly
`.github/workflows/intermediates.yml`, which opens a pull request when the data changes) — do not
edit by hand.

| File | What |
|------|------|
| `manifest.json` | format, date of the data, sources, licence, shard layout, counts, the lifecycle window, a digest of the files and of the manifest itself (the date moves only when one of them does; the skipped counts are in the build log, not here) |
| `ski/<xx>.json` (256) | subject key identifier (hex) → `[{ owner, der }]`: the CCADB CA owner and the base64 DER, sharded by the first two hex digits; each issuer looked up reads one ≈ 16 KB file |
| `dn/<x>.json` (16) | the first 16 hex digits of SHA-256 over a subject DN (as `lib/x509.js` writes it) → subject key identifiers, for a certificate that names no authority key identifier |
| `roots.json` | the roots (SHA-256, CCADB name — made unique with the DN's OU where several share a CN —, owner, key identifier — `null` for a root whose certificate carries none, such as TWCA Global Root CA, which the page then matches by its DN —, DN, expiry, status in the Chrome, Mozilla, Apple and Microsoft stores) and the lifecycle table: distrust-after dates and the roots that expire from January 1 of last year to December 31 of next year |

The intermediates come from two CCADB sources. Mozilla's report lists the ones whose parent in
CCADB is a root Mozilla includes for websites. It misses the hierarchies browsers reach through a
cross-signed root — Let's Encrypt's YE1–YE3 / YR1–YR3 (under Root YE / Root YR, which no store
includes; their ISRG Root X2 / X1 cross-signs are in Mozilla's report), Microsoft's TLS G2 CAs —
and the ones under a root that only other stores keep. So the certificate records add every
intermediate that is TLS capable, trusted by at least one of the Apple, Chrome, Microsoft and
Mozilla stores, not revoked, not expired and not in Mozilla's report (≈ 275 of them), with its PEM
from the PEM report of its notBefore year; the two are de-duplicated by fingerprint.

Kept: CA certificates with a subject key identifier, valid on the build date, whose extended
key usage allows TLS server authentication (serverAuth, anyExtendedKeyUsage or none) — about
2,270 in all. The build writes nothing when a download looks wrong: under 500 intermediates or
100 roots, or one of the well-known current issuers in `CANARIES` (YE1, YR1, R12, Microsoft TLS
G2 RSA CA OCSP 02, WR1, Amazon RSA 2048 M02, Sectigo DV R36; each until its own expiry) missing.
The service worker precaches `manifest.json` and `roots.json` only; the shards are read on use
(the lookup needs a connection).

## `senders/` — the sender lists of DMARC & TLS reports

DMARC & TLS reports names the service behind each sending address of a report. Most names need
no list: `assets/js/lib/senders.js` holds DomainScope's own table of about seventy services (their
SPF includes, DKIM domains, return-path and reverse-DNS domains), and a source is named from its
DKIM signature, its return-path or the SPF include that authorizes it. For the addresses no report
names, **Identify senders** looks up their reverse DNS and matches the names against these lists.
**Generated by `tools/build-senders.mjs`** (maintainers, and the weekly
`.github/workflows/senders.yml`, which opens a pull request when the data changes) — do not edit
by hand.

| File | What |
|------|------|
| `ptr-map.json` | reverse-DNS base domain → `[name, type]` for the map's mail-relevant types (Email Provider, Email Security, Marketing, SaaS, IaaS, PaaS, Web Host, MSP, MSSP, Technology; renamed to `lib/senders.js` types): 1,348 entries, 59 KiB (17 KiB gzip) |
| `isp.json` | the base domains of the map's ISP rows, without names: 950 entries, 16 KiB (5 KiB gzip); a sender there is an ISP or home network — spoofing, or a user forwarding their mail |
| `manifest.json` | format, date of the data, the source (URL, commit, SHA-256, rows, types), the licence and its notice, the SHA-256 and size of each file, the counts per type |

Both lists carry the notice of the changes in their own `notice` field. Rows whose base domain is
not a host name (`deltahost-ptr`) or is a public suffix (`gov.in`) are left out; the other types of
the map (Healthcare, Education, Government …) are not kept. The service worker precaches the
manifest only: the lists are read on an Identify senders click, which needs a connection anyway.

**Why that commit and not the newest.** parsedmarc itself is Apache-2.0, and so was its map until
2026-04-26. Since commit `ec2db72` the maps README distributes `base_reverse_dns_map.csv` under
**CC BY-SA 4.0**, because rows were added from IPinfo Lite (itself CC BY-SA 4.0, bundled with
parsedmarc from 2026-04-23); the map grew from about 3,100 to 38,600 rows that way. CC BY-SA is
share-alike: a copy and what is derived from it must keep that licence, which an MIT project does
not take on for its data (the same reason dmarc.io's CC BY-SA list is not used). The pin is the
map's last commit before IPinfo Lite came in, distributed under the repository's Apache-2.0
licence with no licence of its own. `tools/build-senders.mjs` reads the LICENSE and the maps README
at the commit it builds and refuses to write anything when the map is under a share-alike licence
there, so moving the pin to a newer commit fails until the map's licence allows it.

Apache-2.0 asks that its text and the attribution travel with the data and that changed files say
so: the licence text is in [`THIRD_PARTY_LICENSES.txt`](THIRD_PARTY_LICENSES.txt) (linked from the
About page, which credits parsedmarc), each list and the manifest carry the notice, and the upstream
ships no NOTICE file. Not used: dmarc.io (no `Access-Control-Allow-Origin`, and CC BY-SA 4.0).
