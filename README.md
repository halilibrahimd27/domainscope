# DomainScope

**Open-source SSL & DNS toolkit that runs entirely in your browser.**
Discover the subdomains of a domain, what they resolve to, which hosts hide behind Cloudflare, and **exactly which of your servers a certificate must be installed on**.

## Why

A customer sends you a renewed certificate for `*.example.com`. You manage hundreds of servers. Which ten of them need it?

- Online subdomain finders disagree with each other (5 results here, 9 there), because each one reads different data sources.
- Hosts behind Cloudflare's orange cloud resolve to Cloudflare IPs, so DNS never tells you which origin server is behind them.
- Your server inventory lives in a hosts file, an Ansible inventory or a spreadsheet, and nothing connects it to DNS.

DomainScope combines several sources, resolves every name, classifies each answer (Cloudflare, other CDN, SaaS platform, direct, private, NXDOMAIN, dangling CNAME), and matches the IPs against **your own inventory**, all inside your browser. For hosts behind a proxy, the bundled Python CLI connects to your servers directly with SNI and reports which servers still serve the old certificate.

## Across the tools

- **First visit.** The start page suggests five jobs to begin with (find every subdomain, where a certificate must go, a domain's health, whether a DNS change is live everywhere, import a zone file). They go away once you dismiss them or run anything; About › Where to start keeps them.
- **The current target.** The domain, host name or IP address you last ran something on shows as a chip in the header. Every tool you open next has it filled in and sends nothing until you press its button. A box you have typed in keeps your text, and a box that only holds a carried target follows each newer one. The × on the chip clears it.
- **Workspaces.** The header shows the workspace you work in. Switching asks first when it would stop a running job or drop unsaved server edits. It then forgets the current target and the kept results, which belonged to the other customer, and fills in the new workspace's most recent domain.
- **Kept results.** Coming back to a tool shows its last result again, with "Result from 14:02 · Run again" and no new query, also after a language switch.
- **Copy summary.** Every result has **Copy summary**: 5–12 lines of Markdown for a Jira ticket or a Slack thread (DNS Lookup and IP Intel: one line), in the interface language, with the link to the view and a UTC timestamp; **Plain text** copies the same lines without Markdown. A summary holds only what the page shows and says what is missing: a cancelled or stopped run, passive sources or IP lookups that failed (rate limits included). If the browser blocks the clipboard, the text opens in a dialog to copy by hand.
- **Printing** (Ctrl+P / ⌘P) uses a light, paper-friendly layout in either theme: no navigation, forms or buttons, collapsed sections opened, table rows kept whole, and a header with the page title, the print time (UTC) and the link.
- **Keyboard.** **Ctrl+Enter** (⌘+Enter on a Mac) runs the tool from the field you are in, **Esc** stops a running job (in a table's filter it first clears the text), **/** jumps to the tool's main field and **?** lists the shortcuts.
- **Long jobs.** While a Subdomains, SSL Targets or Bulk Resolve job runs you can work elsewhere: the tab title shows its progress ("(62%) …"), the view's menu entry carries a progress ring and the favicon a badge. After 30 s the job offers **Notify me when done**, a desktop notification whose permission is asked only when you click it. It is not offered in Chrome and other Chromium browsers on Android, which show notifications only through a service worker.
- **Install and offline.** The published site can be installed as an app (the browser's Install button, or Add to Home Screen on a phone). A service worker then keeps the app's own files in the browser, so DomainScope starts without a connection: **Certificate**, **Zone File**, **Servers** and **About** work offline, and the other tools say they need the network instead of failing. A wordlist tier is kept once a scan has used it. When a new version is deployed, an "Update ready" notice with a **Reload** button appears. The development checkout (`npm run serve`) registers no service worker.

## Workspaces

The header shows the workspace you work in (on a phone, the top of the **Tools** menu). Each workspace keeps its own servers, learned names, custom wordlist, **expected CAs**, notes and recent domains: the same address at two customers is no duplicate, and a label learned at one is never tried under another's domains. Theme, language, resolvers and parallelism are the same everywhere; switching is described under [Across the tools](#across-the-tools).

Expected CAs add an "Expected CA" or "Unexpected CA" badge to the issuer in the Certificate view and in SSL Targets › Verify, and to CAA values (Certificate, Domain Health). **Export** writes a workspace as one JSON **hand-over file**, encrypted if you give a password (PBKDF2-SHA-256 with 600,000 iterations, AES-GCM); the password is never stored, and an encrypted file's name leaves the workspace's name out. **Import** opens it as a new workspace, or over the workspace of the same name after a confirmation.

## How it works

DomainScope is a static site with no backend. Everything runs in your browser against public APIs; all of them allow cross-origin requests except where marked:

| Purpose | Services |
|---|---|
| Subdomain sources | [crt.sh](https://crt.sh), [Cert Spotter](https://sslmate.com/certspotter/), [HackerTarget](https://hackertarget.com), [AnubisDB](https://anubisdb.com), [AlienVault OTX](https://otx.alienvault.com), [ip.thc.org](https://ip.thc.org) |
| A host name's certificate | Cert Spotter, crt.sh as fallback (Certificate and SSL Targets, only when you press Load) |
| A domain's certificate issuers | Cert Spotter (one single-host request), crt.sh as fallback (Domain overview › Certificates, only when you press Look up issuers) |
| DNS (RFC 8484 DoH) | Cloudflare, Cloudflare Family, Google Public DNS, Quad9†, Quad9 (ECS)†, Control D, DNS.SB, IIJ Public DNS, CleanBrowsing, Tiarap, seby.io, CZ.NIC ODVR |
| IP data | [RIPEstat](https://stat.ripe.net) (also the owner of an origin network, only when you click "Look up owner", and an AS's announced prefixes in Reverse DNS, only when you press List prefixes), [ipwho.is](https://ipwho.is), HackerTarget reverse IP, ip.thc.org reverse IP (Retire an IP, only when you press Find other names on the address) |
| Registration | RDAP via the IANA bootstrap (Domain Health and Domain overview; some country TLDs, such as `.de`, `.jp` and `.tr`, publish no RDAP) |
| Checks from the internet | [Globalping](https://globalping.io) (jsDelivr's free probe network; only when you press "Check from the internet" in SSL Targets › Verify, or "Check the policy" on Domain Health's MTA-STS card, or "Test … names" in Renewal readiness) |

† Quad9 answers browsers over HTTP/3 without a CORS header, so Chrome, Edge and most other browsers usually cannot read it; Global DNS shows those rows as "Not readable in browsers" with a `dig` command, and discovery leaves Quad9 out of its default resolver chain. It works from a terminal, and in a browser on networks that block QUIC.

Free tiers have rate limits, and they apply **per visitor IP**, not globally: HackerTarget allows about 50 requests per day, Cert Spotter about 10 full-domain searches per hour (a scan uses up to 5 for each registrable domain it covers, so scanning `example.com example.net` together can use all 10) and, separately, 100 single-host requests per hour (loading one host name's certificate costs two, so about 50 lookups, and the Domain overview's Look up issuers one; after a 429 the page searches crt.sh only until the hour is over), and anonymous OTX is limited. Globalping allows 250 probes per hour without an account, shared by everyone behind your IP address; each Verify check costs one probe (a check whose probe fails is retried on another probe, at most 5 extra probes per batch); a Domain Health MTA-STS policy check costs one probe, and a Renewal readiness HTTP-01 test three per name and address family (at most 10 names per test; a test stopped part way keeps what an earlier test measured for the family it missed). The page shows what is left before it sends any target. If a source fails, the scan keeps going: the DNS-first discovery (record mining, wordlist, permutations) needs no third-party quota at all — only public DoH resolvers.

**Privacy.** Certificates and your server inventory are processed locally and never uploaded, except what you choose to check from the internet: the public IP / host name pairs in **Verify**, a domain's MTA-STS policy host and the host names you test in **Renewal readiness** (below). The only data that leaves your browser is what each lookup needs: domain names go to the DNS resolvers and passive sources, and IPs go to the IP data services when you look them up. Loading a certificate by host name sends only that name to Cert Spotter (and crt.sh as fallback), and only after you press Load; **Try a sample** loads a file from this site and sends nothing. A custom wordlist is kept in the current workspace (this browser's IndexedDB). An imported **zone file** is never uploaded and never saved (a proxied record's origin address from it leaves the browser only through the opt-in Verify origin check, below). It is kept only in the tab's memory: a reload, **Forget** or **Delete all local data** clears it. The current target and each tool's last result are kept only in the tab's memory, never uploaded: a reload, closing the tab, switching workspace or **Delete all local data** forgets them. The domains you work on also go to the current workspace's list of recent domains (in IndexedDB; the Workspaces dialog clears it). A result too large to keep in memory (over 4 MiB, or the oldest when all of them pass 16 MiB) is dropped and only its query is filled in again. Nothing about an imported zone becomes the target or reaches a URL. Its **Live check** sends record names and types only, never values or origin addresses, to your DoH resolvers, and only after you click. Internal-looking names are skipped by default, and the hidden targets of proxied records are never queried. Exact-mode scans of the zone's names use the DoH resolvers only. The **DANE / TLSA** check sends only MX and TLSA queries (names and types, never the certificate) to your DoH resolvers, and only after you click. A **Reverse DNS** sweep sends nothing until you press Sweep. It then sends the reverse names (`in-addr.arpa` / `ip6.arpa`) of the addresses, and A / AAAA queries for the PTR names found, to your DoH resolvers only; the network's own name servers see those queries coming from the resolvers. Private and reserved addresses are never sent. Listing an AS's prefixes sends only the AS number to RIPEstat. **Retire an IP** compares the addresses in your browser. Its check sends nothing until you press Check references; it then sends the names it looks up to your DoH resolvers: each domain's own name and records, the host names this page session knows and the zone file's records that point at the address, never a host name the imported zone marks as internal (whatever its scan hand-off toggle says), and the zone's own domain is not filled in when it looks internal (`corp.example.com`); a domain you type in is checked as typed. Only on its own click, the passive lookup sends each public address (never a private one) to HackerTarget and ip.thc.org, and a discovery sends its Small-wordlist guesses as DNS lookups. **Renewal readiness** sends only DNS queries (names and record types) to your DoH resolvers, four of them for the CAA comparison, and only when you press Check readiness or open a shared link; its HTTP-01 test sends the host names you test, with a made-up `/.well-known/acme-challenge/` path, through Globalping, with the same consent and quota as Verify. The **Domain overview** sends nothing until you press Build overview; it then sends the domain's name to your DoH resolvers (its NS, SOA, DS, DNSKEY, MX, TXT, `_dmarc`, CAA and HTTPS records, the addresses of the domain and `www`, and Domain Health's own questions) and to the registry's RDAP server, and to Cert Spotter (crt.sh as fallback) only when you press Look up issuers. The TXT verification tokens it reads are never shown or put in Copy summary: only the service names are. **Verify** sends nothing until you press "Check from the internet". That first reads your free Globalping quota (one request with no targets in it, sent even if you then cancel); each public IP, host name and port pair goes to Globalping only after you confirm, and anyone with the measurement ID can read the results for about six months. Private addresses are never sent. The optional origin check (off by default) also sends an origin IP from your inventory together with the proxied name it serves, so the public measurement shows that this server answers for that name behind the CDN, which is exactly what someone trying to bypass the CDN looks for; turn it on only for origins whose address may be known. Origins taken from an imported zone file are origin checks too: off by default and named in the dialog, and sent only through that opted-in check. The certificate never leaves your browser; the comparison is local. One probe then sends one HTTPS HEAD request to the server (User-Agent "globalping probe"), so only check servers you operate. The consent is asked again in every page session and is never stored. Domain Health's MTA-STS **Check the policy** also sends nothing until you click it; it then reads your free Globalping quota, asks for consent once per page session, and sends the host name `mta-sts.<domain>` and the policy path. One probe sends one HTTPS GET for the policy (User-Agent "globalping probe"), and anyone with the measurement ID can read the result, the policy and the server's response headers included, for about six months. The comparison with the domain's MX hosts happens in your browser. Learned names are off until you turn them on. They are bare labels such as `api`, never full hostnames or IPs, and are kept only in this browser, in the workspace whose scans taught them. Later scans in that workspace do try them as DNS lookups (`api.<domain>`), so resolvers and that domain's name servers see them. **Workspaces** (the inventory, learned names, custom wordlist, expected CAs, notes and recent domains of each) live in this browser's IndexedDB, in the database `ssds.workspaces`; the settings, remembered view options and a pointer to the workspace in use are in its local storage (keys starting with `ssds.`). Both belong to the site's origin: on a GitHub Pages project site (`<user>.github.io/<repo>/`) every other Pages project of the same account shares that origin and can read them, so a copy that keeps customer data should have an origin of its own (a custom domain, or a user / organisation site that holds only this app). A workspace leaves the browser only as a hand-over file you export yourself, encrypted if you give it a password; the password is never stored. **Delete all local data** (Settings or About) deletes every workspace, the IndexedDB database included (also one the page could not open), together with the settings, and says so; if something could not be deleted, it says why. **Copy summary** puts only what the page shows on your clipboard and sends nothing anywhere. Its link carries only the view's own parameters (domain, name, type), never your inventory or a file's contents; SSL Targets names the servers from your list that need the certificate, as its Servers tab does, and IP Intel says only how many addresses are in your list and leaves private addresses and your servers' addresses out of its link. **Notify me when done** asks for your browser's notification permission only when you click it; the choice lasts until you close the page and is never stored, and the notification is shown by your browser. The published site's service worker keeps only the app's own files and the wordlist tiers a scan has used, in this browser's Cache Storage and separately for each copy of the app on an origin; it never caches anything you type, import or look up, nor any answer from a third party. A private key is never needed; if you paste one by mistake, it is ignored and never displayed. A .pfx / .p12 file and its password stay in the tab: the password is used only to read the file and is never saved or sent. The private key is decrypted only if you tick the key check, in memory, to compare it with the certificate, and is then dropped; it is never shown, kept or exported.

## Wordlists and what DNS guessing can find

DNS has no "list every record" query, and providers such as Cloudflare refuse zone transfers. So DomainScope rebuilds the list from four kinds of evidence: names in public certificates and passive DNS, names the zone's own records mention, words from a list, and variations of names already found. Every guess is checked with a real DNS answer, and wildcard look-alikes are dropped.

| Level | Names per domain | Download | Rough time per domain* |
|---|---:|---:|---:|
| Off | none (records + passive sources only) | — | — |
| Small | 159 | built in | seconds |
| **Smart** (default) | ≈ 7,000 | 42 kB | ≈ 1 min |
| Large | ≈ 50,000 | 183 kB (gzip) | ≈ 7 min |
| Huge | ≈ 130,000 | 588 kB (gzip) | ≈ 18 min |

\* The page plans with 120 queries per second at the default Settings parallelism (24 queries in flight); a lower Settings value slows the sweep in proportion. The estimate is deliberately cautious; measured throughput is in [docs/RESEARCH.md](docs/RESEARCH.md#measured-results-2026-09-23).

- **One ranked list, three sizes.** Smart, Large and Huge are the top ≈ 7,000, ≈ 50,000 and ≈ 130,000 names of one ranking built from permissively licensed public lists (SecLists, bitquark, commonspeak2, dnsgen, altdns; see [License](#license)). The files are served by this site, so a scan never fetches a wordlist from a third party.
- **Market word packs** (Smart and up): `tr, de, fr, es, pt, it, nl, pl, ru, ar, ja, zh`, 83–283 generic business and public-service words each. **Auto** picks them from the domain ending, including second-level endings such as `.com.tr` and several packs for multilingual countries (`.ch` → German, French, Italian). A `.com` gets none automatically; choose packs yourself (or none) under Advanced options.
- **Custom wordlist.** Paste names or load a `.txt` file — one per line or separated by commas / spaces; `dev.api` tries a deeper name. They are tried first, in every level from Small up. The file is read in your browser and the list is kept in the current workspace, in this browser.
- **Learned names** (opt-in, off by default). When you turn them on, after each finished scan the left-most labels of the names that resolved under the scanned domains are remembered in this browser, in the current workspace, and tried right after your custom list next time (the 1,000 most frequent). A sister domain that follows the same naming scheme is then covered even if its names are not in any public list. Later scans of *any* domain in the same workspace send these labels as DNS lookups, so keep the switch off, or give them a workspace of their own, when you scan unrelated organisations. They are never used at level **Off**, and **Forget learned names** clears the current workspace's at any time.
- **Courtesy.** Each guess is one A query to public DoH resolvers, spread over the resolver pool; your browser never contacts the domain's web servers. Names a resolver has not cached are passed on to the domain's authoritative nameservers, so a self-hosted nameserver does see the burst. Per domain at most 4,000 / 20,000 / 80,000 / 160,000 candidates (Small / Smart / Large / Huge), 200,000 per scan.
- **Slow sources never hold up the wordlist sweep.** The wildcard check and the wordlist sweep start when the passive sources have answered or 12 seconds after record mining, whichever comes first. The permutation and final resolve stages then wait for the sources, so names that arrive late are included: while a slow source such as crt.sh is still retrying (its status shows it), the results table can stay empty even after the sweep has finished.

**Limits, honestly.** A name that exists only inside one organisation's zone — a product or project name that never appeared in a certificate or in passive DNS — cannot be found by any global wordlist. Add it to your custom wordlist, let learned names carry it over from a related domain, or import the zone export in **Zone File**: only a zone export is complete. A host that answers exactly like its parent's wildcard record is indistinguishable from the wildcard and is dropped. And a proxied record's origin IP is never published in DNS, so the origin panel gives candidates to confirm with the CLI, not answers. Only a zone export holds the exact origins.

## Certificate checks around a renewal

### A certificate without a file

The Certificate view and step 1 of SSL Targets offer a **No file?** block. Type a host name and the page loads the newest currently valid certificate logged for it in Certificate Transparency: from Cert Spotter, or as crt.sh download links when Cert Spotter cannot answer. The certificate is badged "Loaded from Certificate Transparency — the server may serve a different one", with a link to check the servers in SSL Targets; a precertificate says that no final certificate of that issuance is logged yet. A lookup that could not ask every source says so instead of "not found". **Try a sample** loads a bundled, made-up certificate for `example.com` and `example.net`. Neither starts a scan.

### Several certificates at once

A renewal week often brings more than one certificate: an RSA + ECDSA pair for the same names, and a few others. Drop them all in SSL Targets step 1: several files, a folder or several pasted PEM blocks. Certificates with the same names form one set. One scan covers every set's names, and each host gets the set that names it exactly, else the most specific wildcard, else the one that expires last. The **Renewal plan** tab shows which set each of your servers needs (a server × set matrix, labelled cards on a phone), the names no certificate covers and a per-server **Work list (CSV)** (server, IP, names, set, key types, files). Verify checks every set in one queue and compares each name with its own set; a new certificate of another set counts as new and is marked as such. Step 1 warns when last year's certificate is loaded next to its renewal (a server still serving it would count as updated) and when part of a file could not be read. The CLI takes one `--cert` per certificate ([below](#finding-origins-behind-cloudflare-the-cli)).

### PFX / P12 files

A **.pfx / .p12** file (IIS, Windows, Java keystores, many CAs) asks for its password in the Certificate view and in SSL Targets, then loads its certificates like any other file. The private key is never shown or exported: the opt-in **Check that the private key matches the certificate** decrypts it in memory only to say whether it belongs to the server certificate (RSA, EC P-256 / P-384 / P-521). **Download fullchain.pem** gives the server certificate and its intermediates in the order servers send them, without the root or the key. Legacy bundles (3DES, RC2, as Windows and older Java write them) open too; RC4 or public-key-protected bundles are named, with the OpenSSL command that extracts the certificates.

### DANE / TLSA before a renewal

A TLSA record (DANE) that still pins the old certificate or key makes DANE-validating mail senders queue mail for that host, silently, as soon as the new certificate is installed. The **DANE / TLSA** tab of the Certificate view, and the **DANE** tab of SSL Targets, look up the TLSA records at the domain's mail servers (port 25), at the certificate's names and, in SSL Targets, at the covered hosts the scan found (port 443), only when you press **Check TLSA records** (a slow check can be stopped). Each endpoint shows its DNSSEC state and published records; a record that would break gets the exact record to publish first and the wait before installing (2 × TTL). The certificate's own TLSA values are computed locally, and the results export to CSV and JSON.

### CAA restrictions

The Certificate view checks each base domain's CAA records against the certificate's issuer, and reads the RFC 8657 restrictions: `accounturi` (only this ACME account) and `validationmethods` (only these validation methods). It says what they mean for the next renewal, for example "only dns-01 validation is allowed: an HTTP-01 renewal will fail". Domain Health's CAA card lists every issue / issuewild value as usable, restricted (with that renewal note), unsatisfiable or malformed. With expected CAs set in the workspace, the issuer and each CAA value also carry an "Expected CA" or "Unexpected CA" badge.

### Renewal readiness

With 47-day certificates and multi-perspective validation, a renewal that needs a hand fails. `#/renew` checks, per name, what the CA will check: CAA (and its RFC 8657 conditions) against your CA and challenge; the same CAA answer on Cloudflare, Google, DNS.SB and CZ.NIC (a name server that lags behind or fails breaks multi-perspective validation); `_acme-challenge` (a delegation's target, acme-dns, a dangling CNAME a stranger could take over, leftover tokens); DNSSEC; the DNS-01 plugin for the zone's provider (Cloudflare, Route 53, Azure, Google Cloud DNS, DigitalOcean, Hetzner, OVH, GoDaddy, …; Natro, Turhost and İsimtescil have none, so delegate `_acme-challenge`); and the addresses HTTP-01 connects to. A wildcard needs DNS-01, and a wildcard directly under a public suffix (`*.co.uk`, `*.com`) is left out, since no CA issues it. A name whose lookups got no answer in this browser (a rate limit, a dropped connection, one address family unanswered) reads "Could not be checked", never ready. The names can come from a certificate (a file, CT or the sample), which also sets the CA from its issuer; Certificate and SSL Targets link here with the certificate's names. The report has Copy summary, CSV and JSON, and is shareable: `#/renew?names=example.com,*.example.com&ca=letsencrypt&challenge=dns-01`.

The optional **HTTP-01 test** asks Globalping probes in Europe, North America and Asia, over IPv4 and IPv6, for a made-up token under `/.well-known/acme-challenge/` (a 404 is the good answer). An IPv6 address that answers wrongly fails the name; one that refuses or times out while IPv4 passes is a warning with Let's Encrypt, which retries such a connection over IPv4 (other CAs may not). Measurements already paid for are read again for free after a Stop or leaving the view.

### MTA-STS policy check

A browser cannot read `https://mta-sts.<domain>/.well-known/mta-sts.txt` itself, so Domain Health's MTA-STS card fetches it on request through one Globalping probe: **Check the policy (1 Globalping probe)**. The page validates it against RFC 8461: version, mode (enforce / testing / none) and max_age; every MX host matched by an `mx` pattern, wildcards included; HTTP 200 without a redirect; served as text/plain, since strict senders ignore any other type; a valid certificate for `mta-sts.<domain>`; and exactly one valid `_mta-sts` TXT record, without which senders never fetch the policy. Each problem comes with fix advice. A failed MX lookup is reported as "not compared", never as "no MX". The probe cannot open SMTP, so the MX hosts' STARTTLS certificates are not checked. The check never changes the score, and **Report (JSON)** includes it as `mtaStsPolicy`.

## Domain overview

`#/domain?name=example.com` builds one page per domain, only when you press **Build overview** (a link or a carried target only fills the box). Seven cards fill as their lookups land, each with an **Open in <tool>** link carrying the name:

- **Registration** (RDAP): registrar, created / expires with a countdown, status flags (a missing `clientTransferProhibited` called out), DNSSEC delegation. For `.tr`, `.de`, `.jp`, `.ch` and other TLDs without RDAP it says so and links the registry's WHOIS.
- **DNS hosting**: the name servers' provider (Cloudflare, Route 53, Azure, Google Cloud DNS, NS1, DigitalOcean, Hetzner, OVH, GoDaddy, Namecheap, Natro, Turhost, İsimtescil, Wix, Squarespace …), the SOA primary and serial, DNSSEC.
- **Mail**: the MX platform (Microsoft 365, Google Workspace, Zoho, Yandex 360, Proton, Mimecast, Proofpoint, Yaani …), SPF and DMARC in one line each.
- **Web**: the apex and `www` behind a CDN, a platform or direct, and HTTPS records.
- **Certificates**: the CAs CAA allows, read as RFC 8659 reads it (no issue property means any CA, issuewild gets its own row, an unknown tag marked critical blocks every CA); on a click, the issuers of the current certificates from one Cert Spotter request, each marked allowed or not by CAA.
- **SaaS verifications**: the services the TXT tokens name (Google, Microsoft 365, Atlassian, Apple, Meta, DocuSign, Stripe, Zoom, Adobe, HubSpot …), never the tokens.
- **Health**: Domain Health's score and worst problems.

A lookup that failed shows "⚠ n/a" with the reason and a Retry that asks only that lookup again. **Copy summary** gives one line per card, and the page prints one card per block.

## Why Global DNS answers differ

Global DNS names the operator of every answer group and uses only the answers already on the page (no extra requests) to say why they differ. **Differs by design** means every answer is a CDN / GeoDNS edge and the CNAME chains agree up to the CDN. Names before the CDN may differ when they all lead to the same CDN names, as weighted records do; with no records of the type anywhere (AAAA of an IPv4-only CDN name), only the chains are compared. Otherwise a warning says which part looks like propagation or a misconfiguration: NXDOMAIN or SERVFAIL on some sources, direct addresses next to CDN edges, a CNAME that differs before the CDN, or a move between providers. When only the locations differ it is GeoDNS. A filtering resolver's SafeSearch rewrite is its policy and is not counted as a difference, and SERVFAIL everywhere is shown as an error, never as "agree".

## Reverse DNS sweep

The **Reverse DNS** view (`#/ptr`, under IP addresses) looks up the PTR record of every address in an IPv4 network up to a /22 (1,024 addresses), a range (`192.0.2.10-192.0.2.50`, also typed with spaces or an en dash), a list of IPv4 / IPv6 addresses, or an AS. For an AS, one RIPEstat request lists its announced prefixes and you pick which to sweep (up to 1,024 addresses together). IPv6 networks are not swept: a /64 holds 2^64 addresses and nothing lists the ones with a PTR record, so only exact IPv6 addresses are looked up.

Each PTR name is forward-confirmed (FCrDNS): confirmed, does not resolve back, no PTR, NXDOMAIN or SERVFAIL. Names under your focus domain are highlighted and listed first. Provider-generated names (`203-0-113-5.isp.example.net`, dynamic / pool / dsl …) fold into one pattern row with a count. Each address shows its operator (CDN, cloud) and the matching server from your inventory. Export CSV, JSON or `names.txt`, hand the names to a Subdomains scan (exact mode), or add the forward-confirmed hosts to Servers as an unsaved draft in your list's own format. The links from the Subdomains › Origins tab (one per IPv4 origin network) and from Domain Health (one per MX address) only fill the form: the sweep starts when you press Sweep.

## Retiring an IP address

The **Retire an IP** view (`#/retire`, under IP addresses) takes addresses or a network up to a /24 (IPv6: a /120) and the domains to check, filled in from your last scan or imported zone (not the zone's own domain when it looks internal, such as `corp.example.com`). For each domain it resolves its own name, the host names this page session knows (the last Subdomains / SSL Targets scan, the imported zone; a domain without any gets a Small-wordlist discovery offered with its query estimate, never run by itself), its MX and NS hosts, its HTTPS record and its SPF policy with every include. It lists every A / AAAA record, CNAME chain, SPF ip4 / ip6 / a / mx mechanism, MX and NS host (an in-zone name server: its glue at the registrar too) and imported zone record (a wildcard is asked through a random name under it), proxied origins included, that still reaches the address, each checked live over DoH.

SPF follows the include path, and the first match of a policy decides: a carve-out such as `-ip4:` in front of a wider range is kept, a term an earlier one shadows is still to be removed, and an `a/24` or `mx/24` that reaches the address only through its CIDR length is to be narrowed; a macro such as `%{i}` reads "cannot tell". The change list is grouped by domain, worst first (breaks mail, breaks DNS, address record, proxy origin, CNAME chain, zone file only, stale), with what to change and the evidence; your server list says which server owns the address. A failed lookup, a stopped check or a domain that does not exist (a typo?) never reads as "nothing points here". **Find other names on the address** asks HackerTarget and ip.thc.org reverse IP, only on a click (the request count and the free quota are written next to the button, and a list cut off after one page is said); their names stay "unverified until checked" until **Check these too**. Export CSV or JSON, or Copy summary.

## Finding origins behind Cloudflare: the CLI

A browser cannot open raw TLS connections to arbitrary IPs. [`cli/ssl_origin_scan.py`](cli/ssl_origin_scan.py) can. It is a single file that needs Python 3.8+ and no extra packages. Run it from a machine inside your network, such as a jump host. It connects to every server IP in your inventory, requests each hostname via SNI, and compares the certificate it gets back with the new one.

```bash
# Download it from the site or the repo
curl -O https://halilibrahimd27.github.io/domainscope/cli/ssl_origin_scan.py

# Renewal day: which servers still serve the old certificate?
python3 ssl_origin_scan.py -t servers.txt --cert new-cert.pem

# Use the names/targets exported from the web app, on ports 443 and 8443
python3 ssl_origin_scan.py -t targets.txt -n names.txt --cert new-cert.pem -p 443,8443

# Renewal week: an RSA + ECDSA pair and another certificate, checked in one run
python3 ssl_origin_scan.py -t targets.txt -n names.txt --cert new-cert-a-rsa.pem --cert new-cert-a-ecdsa.pem --cert new-cert-b-rsa.pem

# Reports for scripts / Excel, and a CI-friendly exit code
python3 ssl_origin_scan.py -t hosts.ini --cert new.pem --json report.json --csv report.csv --fail-on-needs-update

# Internal hosts signed by your own CA are PRIVATE_CERT, not NEEDS_UPDATE; one server listens on 8443 only
python3 ssl_origin_scan.py -t hosts.ini -t 203.0.113.5:8443 --cert new.pem --private-ca internal-ca.pem

# Find the origin of proxied names: sweep a network the Subdomains page suggested
python3 ssl_origin_scan.py -t 203.0.113.0/24 -n shop.example.com api.example.com

# The same sweep, leaving a mail server and a /28 alone (never connected to)
python3 ssl_origin_scan.py -t 203.0.113.0/24 --exclude 203.0.113.25 203.0.113.64/28 -n shop.example.com

# Exact origins from an imported zone file (Zone File › Origins & servers)
python3 ssl_origin_scan.py -t zone-targets.txt -n zone-names.txt

# Cron: what changed since the last run and certificates expiring within 21 days, posted to
# Slack / Teams / Discord / Telegram / Google Chat (the URL stays out of the shell history)
export DOMAINSCOPE_NOTIFY_URL='https://hooks.slack.com/services/...'
python3 ssl_origin_scan.py -t hosts.ini --cert new.pem --baseline last.json --json last.json --warn-days 21 -q > last.txt
```

It reports one status per server, port and name:

| Status | Meaning |
|---|---|
| `UPDATED` | The server already serves the new certificate. |
| `NEEDS_UPDATE` | The server hosts the name with a different (old) certificate. **Install the new one here.** |
| `ORIGIN_CERT` | The server hosts the name with a Cloudflare Origin CA certificate. Only Cloudflare trusts it, which is right for an origin behind Cloudflare Full (strict) while the name stays proxied. Listed apart, not counted as needing the new certificate. |
| `PRIVATE_CERT` | The server hosts the name with a self-signed certificate, or one issued by a CA you pass with `--private-ca` (usual on internal hosts). Listed apart, not counted as needing the new certificate. |
| `NOT_HOSTED` | The server does not serve this name (it returns its default certificate). |
| `TLS_ERROR` / `TIMEOUT` / `CLOSED` | Unreachable, or the handshake failed. |

`ORIGIN_CERT` and `PRIVATE_CERT` keep the to-do list to the servers that really lag behind; `--strict-public` counts them as `NEEDS_UPDATE` again. `--private-ca FILE` (PEM, DER or P7B, repeatable) takes the CA that signs your internal server certificates; the issuer name and, when both certificates carry one, the key identifier must match. When the new certificate is itself an Origin CA, self-signed or private-CA certificate, older ones of the same kind stay `NEEDS_UPDATE`.

`--cert` can be repeated (an RSA + ECDSA pair, or several certificates renewed together): every file's names are probed, a server serving any of them is `UPDATED`, and the reports name which one (`matches FILE` in the summary, `newCertFile` and `newCertificates[].file` in the JSON, a last `new_cert` column in the CSV). SSL Targets offers one file per certificate (`new-cert-a-rsa.pem`, `new-cert-a-ecdsa.pem`, …) and the matching command. A `--cert` whose names are all in a newer `--cert` with the same key type gets a warning: last year's certificate passed by mistake would make a server still serving it `UPDATED`. With one `--cert` the reports are unchanged.

Targets can be IPs, CIDRs, ranges, hostnames or inventory files, in the same formats the web app accepts. An address or hostname written with a port (`203.0.113.10:8443`, `[2001:db8::10]:8443`, `web01.example.com:8443`, or `web01 203.0.113.10:8443` in a file) is scanned on that port **instead of** `-p`; `-p` applies to every target written without one, and a target listed both ways gets both. IPv6 needs the brackets. A port outside 1–65535 is a usage error on the command line and a warning in a file (JSON values included), never a silently dropped target; so is a hostname with a port next to an address on the same line (write the address with the port). In an Ansible INI inventory — a line under a `[group]` header or with `ansible_*` variables — a port on the host at the start of the line (`203.0.113.10:2222`, `web01.example.com:2222`) is Ansible's SSH port, as Ansible reads it: that host is scanned on `-p`, with a warning, so leave the SSH port there and give the TLS ports with `-p`. One address listed for different servers on different ports is not a duplicate. The Servers view, the `targets.txt` exports and the Verify tab's CLI card keep these ports. `--exclude` takes IPs, CIDRs, ranges or a file of them; it is applied after names are resolved and before any connection. Excluded addresses are listed in the summary, the JSON and the CSV (`EXCLUDED`). Numeric "hostnames" such as `2026092401`, `127.1` or `0x7f.0x1` are refused, because the system resolver would read them as an IPv4 address. Addresses with a leading zero (`010.0.0.1`) are refused too. `0.0.0.0/8`, multicast and broadcast addresses are never scanned. In the `targets.txt` of the Servers view and SSL Targets each server name is one CLI token: spaces, `#`, `;`, `,`, `=`, `/`, `:` and control characters become `_` (`Web Server 1` → `Web_Server_1`) and a name that is an IP address or range is dropped, so the CLI never merges, splits or comments out a server. Exit codes: 0 done, 1 `NEEDS_UPDATE` found (only with `--fail-on-needs-update`; `ORIGIN_CERT` and `PRIVATE_CERT` servers do not trigger it unless `--strict-public` is given), 2 usage error, 3 a report file could not be written after the scan, 4 something changed since `--baseline` (only with `--fail-on-change`), 5 the `--notify` message was not delivered (only with `--fail-on-notify-error`), 130 interrupted. When several apply, 3 comes first, then 5, 4 and 1. Run `python3 ssl_origin_scan.py --help` for everything else.

**Monitoring between visits.** `--baseline previous.json` compares the scan with an earlier `--json` report per IP, port and name: another served certificate, a status that moved (for example `UPDATED` → `NEEDS_UPDATE`, or a new `TLS_ERROR`), and endpoints or names that are new or gone. `--warn-days N` lists the served certificates that expire within N days. `--notify URL`, or `DOMAINSCOPE_NOTIFY_URL`, posts a short summary only when something changed or expires: to a Slack, Microsoft Teams / Power Automate, Discord, Telegram or Google Chat webhook, or as JSON to any other URL. A move from one failure state to another (`CLOSED` → `TIMEOUT`) is listed but does not trigger a message or `--fail-on-change`. The URL is never printed. Give the same file to `--baseline` and `--json` to compare each run with the one before. If a message with changes cannot be delivered, the file keeps the previous report, so the next run reports those changes again.

The origin panel (Subdomains › Origins) and the Behind CDN tab (SSL Targets) write the sweep command for you, for **Linux / macOS** (`python3 …`) or **Windows PowerShell** (`python …`). IPv4 networks go in as the /24 when several origins or one of your inventory servers sit in it. Otherwise they go in as the exact addresses, and so does a /24 in shared cloud / hosting / CDN space that holds none of your servers. IPv6 always goes in as exact addresses (a /48 is far too large to sweep). Addresses you enter under **Exclude addresses** become `--exclude`; a network they cover entirely drops out. They are kept for that scan while you move between pages, and the JSON export's `origin.cliSuggestion` carries the same `--exclude` (POSIX form). A target list too long for one command line is read from `proxied-targets.txt` instead (Verify's CLI card: `verify-targets.txt`), offered as a download next to `names.txt`. The Zone File view uses only the exact origins from the file: addresses and host names, never a /24, with `*.x` names quoted. Every target must be an IP address or network and every name a valid hostname: anything else — for example a hostile name taken from a CT log — is left out and counted, never pasted into the command, and the remaining tokens are quoted for the chosen shell. The Certificate view's `openssl s_client` line follows the same rule: it uses a certificate name only when it passes (a wildcard as `www.<base>`), else `example.com`. Each IPv4 origin network in Subdomains › Origins also links to a [Reverse DNS sweep](#reverse-dns-sweep) of it, which can name hosts the scan did not find.

## Nightly checks without a browser tab: the headless runner

A closed browser tab monitors nothing. [`tools/ds.mjs`](tools/ds.mjs) runs six of the app's checks under Node 22+ with the app's own libraries (no dependency, no build step): `health` (Domain Health), `subdomains` (discovery, or `--exact` for the names you list), `drift` (a zone export against live DNS), `ct` (current certificates and their issuers in Certificate Transparency), `renew` (renewal readiness) and `dane` (the TLSA check of a certificate). Each prints a short summary and writes a JSON report (`--json`) and a Markdown summary (`--md`). With `--baseline` it compares the run with the previous report of the same command and opens with "Changes since the baseline": hosts that appear or go, health findings and the score, new certificate issuers or names, zone record sets whose live state moved, renewal verdicts.

```bash
node tools/ds.mjs health example.com example.org --json health.json --md health.md
node tools/ds.mjs ct --list domains.txt --baseline ct.json --json ct.json --fail-on-change
node tools/ds.mjs --help
```

Exit codes: 0 done, 1 the run failed, 2 usage error (report files and the baseline are checked before anything is sent), 3 a report could not be written after the run, 4 something changed since `--baseline` (only with `--fail-on-change`), 130 interrupted (nothing written). DNS goes through the app's DoH resolvers with the app's limits (Quad9 and CZ.NIC answer over HTTP/2 only, which Node's fetch does not speak), and nothing goes to Globalping.

[`docs/examples/nightly-domainscope.yml`](docs/examples/nightly-domainscope.yml) runs it every night on GitHub Actions: it commits the reports and keeps one issue open while something changed ([setting it up](docs/examples/README.md)). **Use it in a private repository**, since the results name your hosts, their addresses and your DNS records. **Never commit inventories or zone files unless you mean to.** **No secret is needed**: the workflow's own token commits the results and writes the issue.

## A typical SSL rollout

0. **Subdomains (optional):** see everything first — every name, which are proxied, and the origin networks with a sweep command for your shell, e.g. `python3 ssl_origin_scan.py -t 203.0.113.0/24 -n api.example.com shop.example.com`. If you can export the zone, drop it in **Zone File** instead: you get every name and the exact origin of each proxied record, then **Find certificate targets** or copy the exact sweep command.
1. **SSL Targets:** drop in the new certificate, confirm the domain, and scan. Your inventory is matched automatically. Renewing several certificates at once (an RSA + ECDSA pair, a few others)? Drop them all, or their folder: they are grouped into sets, one scan covers them, and the **Renewal plan** tab lists which set each server needs, with a CSV work list.
2. **Servers tab:** lists the servers whose DNS points at a covered name. **Behind CDN tab:** lists the proxied hosts, their origin hints, and the CLI command.
3. **DANE tab** (if the domain receives mail or uses DANE): press **Check TLSA records**. A record that still pins the old certificate or key is listed with the record to add: publish it, wait 2 × TTL, then install.
4. Install the certificate, then open the **Verify** tab and press **Check from the internet**: every public server is checked for every name it should serve, and "Check again" re-checks only what is not done yet. For private addresses and origins behind a CDN, run the CLI command the tab gives you (`--cert new-cert.pem`; with several certificates one `--cert` per certificate, each offered as a download). Repeat until every server reports `UPDATED`.

```bash
npm test                 # JavaScript unit tests (node --test "tests/js/*.test.js"; `node --test tests/js/` is equivalent)
npm run test:py          # CLI tests
npm run test:e2e:offline # the offline E2E suites (shell, zone, verify, renewal, dane, pfx, renew, ptr, retire, carry, workspaces, domain, and the offline steps of subdomains, global, ip, lookup and health; needs Chrome or Edge), as CI runs them
node tests/e2e/run-all.mjs   # every E2E suite, most against live APIs; verify, renewal, dane, pfx, renew, ptr, retire, carry, workspaces and domain are offline (verify: 0 Globalping probes; renew: a fake DoH and a fake Globalping)

node tools/ds.mjs --help     # the headless runner: its commands, options and exit codes (tests: tests/js/ds-runner.test.js, offline)
```

The bundle preview installs the site's service worker on http://127.0.0.1:8080/. Without a version argument the bundle is named after its content (`v/dev-<hash>/`), so assembling again after an edit brings "Update ready"; `npm run serve` on the same port replaces the worker and deletes its caches. To start from scratch, clear the site data for 127.0.0.1:8080. `tests/js/start-route.test.js` keeps what the start page downloads under a 370 KB gzip budget (the workspace store opens before the first view).

Tests and docs use reserved example names (`example.com`, `example.net`) and documentation IP ranges (`192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`); `tests/js/repo-hygiene.test.js` fails on any other IPv4 address that is not well-known public infrastructure. Live scripts read your own targets only from the gitignored `tests/live/targets.local.json`.

Contributions are welcome. Keep it dependency-free, DOM-free in `lib/`, and CSP-safe (never assign untrusted data to `innerHTML`).
