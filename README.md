# DomainScope

**Open-source SSL & DNS toolkit that runs entirely in your browser.**
Discover the subdomains of a domain, what they resolve to, which hosts hide behind Cloudflare, and **exactly which of your servers a certificate must be installed on**.

## Why

A customer sends you a renewed certificate for `*.example.com`. You manage hundreds of servers. Which ten of them need it?

- Online subdomain finders disagree with each other (5 results here, 9 there), because each one reads different data sources.
- Hosts behind Cloudflare's orange cloud resolve to Cloudflare IPs, so DNS never tells you which origin server is behind them.
- Your server inventory lives in a hosts file, an Ansible inventory or a spreadsheet, and nothing connects it to DNS.

DomainScope combines several sources, resolves every name, classifies each answer (Cloudflare, other CDN, SaaS platform, direct, private, NXDOMAIN, dangling CNAME), and matches the IPs against **your own inventory**, all inside your browser. For hosts behind a proxy, the bundled Python CLI connects to your servers directly with SNI and reports which servers still serve the old certificate.

## Across the tools

- **First visit.** The start page suggests five jobs to begin with (find every subdomain, where a certificate must go, a domain's health, whether a DNS change is live everywhere, import a zone file). They go away once you dismiss them or run anything; About › Where to start keeps them.
- **The current target.** The domain, host name or IP address you last ran something on shows as a chip in the header. Every tool you open next has it filled in and sends nothing until you press its button. A box you have typed in keeps your text, and a box that only holds a carried target follows each newer one. The × on the chip clears it.
- **Workspaces.** The header shows the workspace you work in. Switching asks first when it would stop a running job or drop unsaved server edits. It then forgets the current target and the kept results, which belonged to the other customer, and fills in the new workspace's most recent domain.
- **Kept results.** Coming back to a tool shows its last result again, with "Result from 14:02 · Run again" and no new query, also after a language switch.
- **Copy summary.** Every result has **Copy summary**: 5–12 lines of Markdown for a Jira ticket or a Slack thread (DNS Lookup and IP Intel: one line), in the interface language, with the link to the view and a UTC timestamp; **Plain text** copies the same lines without Markdown. In the DNS change request it is on the **is it live?** page (the form's instructions are the text to paste there). A summary holds only what the page shows and says what is missing: a cancelled or stopped run, passive sources or IP lookups that failed (rate limits included). If the browser blocks the clipboard, the text opens in a dialog to copy by hand.
- **Printing** (Ctrl+P / ⌘P) uses a light, paper-friendly layout in either theme: no navigation, forms or buttons, collapsed sections opened, table rows kept whole, and a header with the page title, the print time (UTC) and the link.
- **Keyboard.** **Ctrl+Enter** (⌘+Enter on a Mac) runs the tool from the field you are in, **Esc** stops a running job (in a table's filter it first clears the text), **/** jumps to the tool's main field and **?** lists the shortcuts.
- **Long jobs.** While a Subdomains, SSL Targets, Bulk Resolve or Domain portfolio job runs you can work elsewhere: the tab title shows its progress ("(62%) …"), the view's menu entry carries a progress ring and the favicon a badge. After 30 s the job offers **Notify me when done**, a desktop notification whose permission is asked only when you click it. It is not offered in Chrome and other Chromium browsers on Android, which show notifications only through a service worker.
- **What this page sent.** About › What this page sent (the footer link, which counts the requests, opens it) lists every host this page has contacted since it was opened, as your browser measured it, with the number of requests and what kind of data each received: DNS names and types for the DoH resolvers, domain names for the CT and passive sources, IP addresses, IP / host name pairs, DNS questions and name servers for Globalping, a serial number or a public-key hash. A registry of endpoints, kept in step with the code by a test, says what each host gets; a host not in it (a browser extension's request) is listed first, flagged. It also says what is never sent and, on the published site, which deploy runs. Nothing is stored: a reload or **Clear** starts from zero.
- **Install and offline.** The published site can be installed as an app (the browser's Install button, or Add to Home Screen on a phone). A service worker then keeps the app's own files in the browser, so DomainScope starts without a connection: **Certificate**, **Certificate estate**, **Zone File**, **DNS change request**, **DMARC & TLS reports**, **Servers** and **About** work offline, and the other tools say they need the network instead of failing. Their own network steps (a missing intermediate, Key continuity, the change request's Read and check page, the reports' SPF lookup, New name servers, the zone fetch from deSEC or DigitalOcean) wait for a connection and say so. A wordlist tier is kept once a scan has used it. When a new version is deployed, an "Update ready" notice with a **Reload** button appears. The development checkout (`npm run serve`) registers no service worker.

## Workspaces

The header shows the workspace you work in (on a phone, the top of the **Tools** menu). Each workspace keeps its own servers, learned names, custom wordlist, **expected CAs**, notes, recent domains, the Domain portfolio's policy and **origin map**: the same address at two customers is no duplicate, and a label learned at one is never tried under another's domains. Theme, language, resolvers and parallelism are the same everywhere; switching is described under [Across the tools](#across-the-tools).

Expected CAs add an "Expected CA" or "Unexpected CA" badge to the issuer in the Certificate view and in SSL Targets › Verify, and to CAA values (Certificate, Domain Health). **Export** writes a workspace as one JSON **hand-over file**, encrypted if you give a password (PBKDF2-SHA-256 with 600,000 iterations, AES-GCM); the password is never stored, and an encrypted file's name leaves the workspace's name out. **Import** opens it as a new workspace, or over the workspace of the same name after a confirmation.

## Origin map

A proxied name's real server is found once (by a CLI sweep, a zone file or a server comparison) and is then remembered in the workspace, so the next scan starts from it; Verify checks the remembered origins again. **Servers › Origin map** holds the switch **Remember origins in this workspace**: it is off by default, and while it is off nothing is written to the map (the tools that would write say so); turning it off later keeps the entries, and they are still used until you delete them. Each entry is a name (`*.example.com` covers the names directly under it; a check that finds one of them elsewhere sets the wildcard aside for that name only), the address and port that serve it, the source, when it was first seen and last confirmed, the server of your list it belongs to and whether it is stale.

- **Filled from:** Zone File › Origins & servers (**Remember these origins**), the CLI's `--json` reports imported in that tab (a server answering UPDATED, NEEDS_UPDATE, ORIGIN_CERT or PRIVATE_CERT, that is with a certificate covering a name behind a CDN; the same reader as Certificate estate), SSL Targets › Verify's origin checks of remembered and zone-file origins (never of a candidate an SPF, MX or sibling hint suggested: a server that answers for a name, with a shared wildcard certificate say, is not shown to be its origin), Retire an IP's old and new server comparison (**Remember … as the origin of …**), and by hand: add, change, delete.
- **Used by:** Subdomains and SSL Targets rank a remembered origin above every other candidate ("Remembered"), SSL Targets › Behind CDN lists them, and the CLI sweep command probes them exactly (`ip`, or `ip:port` on another port; never widened to a /24); an origin on another port is checked by Verify and written to `targets.txt` on that port. A server of your list marked `terminates_tls=no` that the map remembers as the origin of a name still gets the certificate ([details](#load-balancers-vips-and-nat)).
- **Stale:** a later CLI report or Verify check that asked the remembered address and found the name not served there (or got no answer, a closed port included, while it found the name on another server), or a zone file that names another origin, marks the entry stale with the reason; an origin a run did not ask stays as it is, since a name can have several. CLI reports and Verify checks land the same whatever order they come in (what a newer run ruled out stays ruled out); a zone file, which names no port, is best remembered in date order with them. No date is taken beyond today. A stale entry is shown, also in results already on screen (they follow the map at once), but no longer used or put in the command; **Remove the stale entries** or a newer confirmation clears it.

The map is kept with the workspace in this browser's IndexedDB and sent nowhere. It leaves the browser only inside a workspace hand-over file you export yourself (importing one that remembers origins says it turns that on); **Forget the origin map**, deleting the workspace or **Delete all local data** removes it. When browser storage is unavailable the map lasts until the tab is closed, and the tab says so.

## How it works

DomainScope is a static site with no backend. Everything runs in your browser against public APIs; all of them allow cross-origin requests except where marked:

| Purpose | Services |
|---|---|
| Subdomain sources | [crt.sh](https://crt.sh), [Cert Spotter](https://sslmate.com/certspotter/), [HackerTarget](https://hackertarget.com), [AnubisDB](https://anubisdb.com), [AlienVault OTX](https://otx.alienvault.com), [ip.thc.org](https://ip.thc.org) |
| A host name's certificate | Cert Spotter, crt.sh as fallback (Certificate and SSL Targets, only when you press Load) |
| A domain's certificate issuers | Cert Spotter (one single-host request), crt.sh as fallback (Domain overview › Certificates, only when you press Look up issuers; Domain Health's Show the fix of a missing CAA record, only when you press Look up the CAs) |
| A certificate's public key | crt.sh (Certificate › CT logs › Key continuity, only when you press Look this key up in CT; only the key's SHA-256 is sent) |
| DNS (RFC 8484 DoH) | Cloudflare, Cloudflare Family, Google Public DNS, Quad9†, Quad9 (ECS)†, Control D, DNS.SB, IIJ Public DNS, CleanBrowsing, Tiarap, seby.io, CZ.NIC ODVR (the DNS change request's check page asks Cloudflare, Google, DNS.SB and CZ.NIC); AliDNS's JSON API for Global DNS's mainland China locations (A, AAAA, CNAME and HTTPS only, plus one question per A / AAAA check on behalf of a US subnet; its RFC 8484 endpoint sends no CORS header) |
| Your DNS provider | deSEC, DigitalOcean (Zone File › Fetch, only when you press Fetch zone, with the API token you paste) |
| IP data | [RIPEstat](https://stat.ripe.net) (also the owner of an origin network, only when you click "Look up owner", and an AS's announced prefixes in Reverse DNS, only when you press List prefixes), [ipwho.is](https://ipwho.is) (also a sending address in DMARC & TLS reports, only when you press Look up), HackerTarget reverse IP, ip.thc.org reverse IP (Retire an IP, only when you press Find other names on the address) |
| Registration | RDAP: each registry's own server from the IANA bootstrap, rdap.org only as the fallback, at most one request a second (Domain Health, Domain overview and Domain portfolio; some country TLDs, such as `.de`, `.jp` and `.tr`, publish no RDAP) |
| Checks from the internet | [Globalping](https://globalping.io) (jsDelivr's free probe network; only when you press "Check from the internet" in SSL Targets › Verify, "Check the policy" on Domain Health's MTA-STS card, "Test … names" in Renewal readiness, "Compare … record sets" in Zone File › New name servers, or "Compare (2 probes)" in Retire an IP) |
| The missing intermediate | This site's own copy of the [CCADB](https://www.ccadb.org/) list of public intermediates (`assets/data/intermediates/`; one or two small files per lookup) |

† Quad9 answers browsers over HTTP/3 without a CORS header, so Chrome, Edge and most other browsers usually cannot read it; Global DNS shows those rows as "Not readable in browsers" with a `dig` command, and discovery leaves Quad9 out of its default resolver chain. It works from a terminal, and in a browser on networks that block QUIC.

Free tiers have rate limits, and they apply **per visitor IP**, not globally: HackerTarget allows about 50 requests per day, Cert Spotter about 10 full-domain searches per hour (a scan uses up to 5 for each registrable domain it covers, so scanning `example.com example.net` together can use all 10) and, separately, 100 single-host requests per hour (loading one host name's certificate costs two, so about 50 lookups, and the Domain overview's Look up issuers one; after a 429 the page searches crt.sh only until the hour is over), and anonymous OTX is limited. The page shows what is left before it sends any target. ## Wordlists and what DNS guessing can find

DNS has no "list every record" query, and providers such as Cloudflare refuse zone transfers. So DomainScope rebuilds the list from four kinds of evidence: names in public certificates and passive DNS, names the zone's own records mention, words from a list, and variations of names already found. Every guess is checked with a real DNS answer, and wildcard look-alikes are dropped.

| Level | Names per domain | Download | Rough time per domain* |
|---|---:|---:|---:|
| Off | none (records + passive sources only) | — | — |
| Small | 159 | built in | seconds |
| **Smart** (default) | ≈ 7,000 | 42 kB | ≈ 1 min |
| Large | ≈ 50,000 | 183 kB (gzip) | ≈ 7 min |
| Huge | ≈ 130,000 | 588 kB (gzip) | ≈ 18 min |

\* The page plans with 120 queries per second at the default Settings parallelism (24 queries in flight); a lower Settings value slows the sweep in proportion. The estimate is deliberately cautious; measured throughput is in [docs/RESEARCH.md](docs/RESEARCH.md#measured-results-2026-09-23).

- **One ranked list, three sizes.** Smart, Large and Huge are the top ≈ 7,000, ≈ 50,000 and ≈ 130,000 names of one ranking built from permissively licensed public lists (SecLists, bitquark, commonspeak2, dnsgen, altdns; see [License](#license)). The files are served by this site, so a scan never fetches a wordlist from a third party.
- **Market word packs** (Smart and up): `tr, de, fr, es, pt, it, nl, pl, ru, ar, ja, zh`, 83–283 generic business and public-service words each. **Auto** picks them from the domain ending, including second-level endings such as `.com.tr` and several packs for multilingual countries (`.ch` → German, French, Italian). A `.com` gets none automatically; choose packs yourself (or none) under Advanced options.
- **Custom wordlist.** Paste names or load a `.txt` file — one per line or separated by commas / spaces; `dev.api` tries a deeper name. They are tried first, in every level from Small up. The file is read in your browser and the list is kept in the current workspace, in this browser.
- **Learned names** (opt-in, off by default). When you turn them on, after each finished scan the left-most labels of the names that resolved under the scanned domains are remembered in this browser, in the current workspace, and tried right after your custom list next time (the 1,000 most frequent). A sister domain that follows the same naming scheme is then covered even if its names are not in any public list. Later scans of *any* domain in the same workspace send these labels as DNS lookups, so keep the switch off, or give them a workspace of their own, when you scan unrelated organisations. They are never used at level **Off**, and **Forget learned names** clears the current workspace's at any time.
- **Courtesy.** Each guess is one A query to public DoH resolvers, spread over the resolver pool; your browser never contacts the domain's web servers. Names a resolver has not cached are passed on to the domain's authoritative nameservers, so a self-hosted nameserver does see the burst. Per domain at most 4,000 / 20,000 / 80,000 / 160,000 candidates (Small / Smart / Large / Huge), 200,000 per scan.
- **Slow sources never hold up the wordlist sweep.** The wildcard check and the wordlist sweep start when the passive sources have answered or 12 seconds after record mining, whichever comes first. The permutation and final resolve stages then wait for the sources, so names that arrive late are included: while a slow source such as crt.sh is still retrying (its status shows it), the results table can stay empty even after the sweep has finished.

**Limits, honestly.** A name that exists only inside one organisation's zone — a product or project name that never appeared in a certificate or in passive DNS — cannot be found by any global wordlist. Add it to your custom wordlist, let learned names carry it over from a related domain, or import the zone export in **Zone File**: only a zone export is complete. A host that answers exactly like its parent's wildcard record is indistinguishable from the wildcard and is dropped. And a proxied record's origin IP is never published in DNS, so the origin panel gives candidates to confirm with the CLI, not answers. Only a zone export holds the exact origins.

## Certificate checks around a renewal

### A certificate without a file

The Certificate view and step 1 of SSL Targets offer a **No file?** block. Type a host name and the page loads the newest currently valid certificate logged for it in Certificate Transparency: from Cert Spotter, or as crt.sh download links when Cert Spotter cannot answer. The certificate is badged "Loaded from Certificate Transparency — the server may serve a different one", with a link to check the servers in SSL Targets; a precertificate says that no final certificate of that issuance is logged yet. A lookup that could not ask every source says so instead of "not found". **Try a sample** loads a bundled, made-up certificate for `example.com` and `example.net`. Neither starts a scan.

### Several certificates at once

A renewal week often brings more than one certificate: an RSA + ECDSA pair for the same names, and a few others. Drop them all in SSL Targets step 1: several files, a folder or several pasted PEM blocks. Certificates with the same names form one set. One scan covers every set's names, and each host gets the set that names it exactly, else the most specific wildcard, else the one that expires last. The **Renewal plan** tab shows which set each of your servers needs (a server × set matrix, labelled cards on a phone), the names no certificate covers and a per-server **Work list (CSV)** (server, IP, names, set, key types, files). Verify checks every set in one queue and compares each name with its own set; a new certificate of another set counts as new and is marked as such. Step 1 warns when last year's certificate is loaded next to its renewal (a server still serving it would count as updated) and when part of a file could not be read. The CLI takes one `--cert` per certificate ([below](#finding-origins-behind-cloudflare-the-cli)).

### Load balancers, VIPs and NAT

DNS answers with the address a client connects to, which is not always where TLS ends. Optional keys on a server's line in **Servers** (or as CSV columns, Ansible host variables, JSON / YAML keys) say where it does; the CLI reads the same keys:

```
lb01  203.0.113.2  ports=443,8443 vip=203.0.113.50 backends=web01,web02
lb02  203.0.113.3  vip=203.0.113.50 backends=web01,web02
web01 10.0.0.21    terminates_tls=no
web02 10.0.0.22    ports=8443
app01 10.0.0.30    nat=203.0.113.10
```

- `ports=443,8443`: the server's TLS ports, used instead of `-p` for its addresses written without a port. In JSON and YAML write `tls_ports` (`tls_ports=` works everywhere): a `ports` key there — Shodan's list of open ports, an Ansible variable — is read as before. Ports that usually carry no TLS (22, 25, 80, 3306 …) are kept with a warning.
- **Precedence of the ports:** an address written with its own port (`203.0.113.10:8443`) keeps exactly that port; one written without is scanned on the server's `ports=`; without those, on the CLI's `-p`.
- `terminates_tls=no`: a server that never gets the certificate — a plain-HTTP backend, or a load balancer that passes TLS through to its backends. Given both ways, yes wins (the safe value) and you get a warning.
- `vip=`: an address an HA pair shares. DNS answers with it match both servers, and the certificate goes on both.
- `backends=web01,web02`: a load balancer and the servers it forwards to.
- `nat=`: the public address DNS answers with for this private server.

SSL Targets › Servers then lists each load balancer, a VIP pair together, with its backends under it: "VIP 203.0.113.50 — install on both: lb01 and lb02", "Behind lb01, lb02 — plain HTTP, no certificate needed", "Behind lb01, lb02 — re-encrypts: install here too", "Reached at 203.0.113.10 (NAT) → 10.0.0.30". The Renewal plan and its work list, the Servers CSV (a last `Topology` column) and the Verify tab follow the same rules, and `targets.txt` carries the keys.

**When the inventory and DNS disagree, the certificate wins.** A server marked `terminates_tls=no` that DNS reaches directly (or that the [origin map](#origin-map) remembers as the origin of a name) still needs the certificate, and its note says "DNS points here directly but the inventory says terminates_tls=no — check the inventory"; the scan never quietly answers "no certificate needed". Warnings name what looks wrong, in the Servers view and in SSL Targets (step 3 and the Servers tab), since they change where the certificate goes: a malformed value, a key a letter off (`backend=` — "did you mean backends=?"; it is not read), TLS that terminates nowhere (a passthrough load balancer whose backends all say `terminates_tls=no`), the holders of one VIP that disagree, backends that loop, a `vip=` or `nat=` address that is a server's own. Ansible group variables are not read for these keys. Without the keys nothing changes.

### PFX / P12 files

A **.pfx / .p12** file (IIS, Windows, Java keystores, many CAs) asks for its password in the Certificate view and in SSL Targets, then loads its certificates like any other file. The private key is never shown or exported: the opt-in **Check that the private key matches the certificate** decrypts it in memory only to say whether it belongs to the server certificate (RSA, EC P-256 / P-384 / P-521). **Download fullchain.pem** gives the server certificate and its intermediates in the order servers send them, without the root or the key. Legacy bundles (3DES, RC2, as Windows and older Java write them) open too; RC4 or public-key-protected bundles are named, with the OpenSSL command that extracts the certificates.

### Missing intermediate and root-store warnings

A server that sends its certificate without the intermediate works in most desktop browsers (they cache or fetch intermediates) but fails in Android, curl, Java and most API clients. A page cannot fetch the certificate's AIA URL itself (plain `http://`, no CORS), so DomainScope ships the Common CA Database (CCADB) list of public TLS intermediates (about 2,270), rebuilt every week by a pull request. When a loaded file stops short of a root, the Certificate view and SSL Targets step 1 — PFX / P12 bundles and certificates from Certificate Transparency too — look up the issuer by its authority key identifier (by the issuer's name when the certificate has none), up to four levels, and pick the way to the root that the most root stores trust: a cross-signed copy under a removed root loses to the one under the current root. **Download fullchain.pem** gives the server certificate and the intermediates in order, never the root or a key; each added intermediate is named with its CA owner and expiry, and the Chain tab says which stores (Chrome, Mozilla, Apple, Microsoft) trust the root the chain ends at.

**Root store warnings** in the Certificate view name a root that a store distrusts for certificates issued after a date (Chrome counts the earliest embedded SCT: Entrust, Chunghwa Telecom, Netlock …), with the date and a link to the announcement; for a certificate issued before the cut-off they say that its renewal has to chain to another root. They also name a removed root, a root kept for other uses only, and a root that expires before the certificate. An intermediate the list does not hold (a private CA, a very new or withdrawn intermediate) is reported as such, with a pointer to the CA's bundle. The lookup needs a connection; the certificate is never sent anywhere.

### Does this CSR match?

Certificate › PEM & OpenSSL › **Does this CSR match?** compares a pasted CSR's public key with the certificate's, in the browser (Ctrl+Enter in the box): a match means the certificate was issued for this key, and the names the CSR asked for are listed. No private key is ever needed; one pasted there by mistake, even only its first lines, is dropped at once and never read. The CLI's `bundle-check` does the same with files, before the certificate exists too ([below](#finding-origins-behind-cloudflare-the-cli)).

### DANE / TLSA before a renewal

A TLSA record (DANE) that still pins the old certificate or key makes DANE-validating mail senders queue mail for that host, silently, as soon as the new certificate is installed. The **DANE / TLSA** tab of the Certificate view, and the **DANE** tab of SSL Targets, look up the TLSA records at the domain's mail servers (port 25), at the certificate's names and, in SSL Targets, at the covered hosts the scan found (port 443), only when you press **Check TLSA records** (a slow check can be stopped). Each endpoint shows its DNSSEC state and published records; a record that would break gets the exact record to publish first and the wait before installing (2 × TTL). The certificate's own TLSA values are computed locally, and the results export to CSV and JSON.

### Related domains and key continuity

A certificate names every host it is for, so one issued for `shop.example.com` and `shop.example.net` says the two belong together. Subdomains › Sources › **Related domains in the same certificates** lists the other registrable domains of the scanned hosts' certificates, read from the Certificate Transparency answers the scan already has (nothing is sent again): how many certificates each one shares, which ones, and **Scan too**, which scans it together with your domains. A certificate naming more than 12 registrable domains is usually a CDN's or a host's certificate for many customers, so domains seen only there fold into a separate list, still with Scan too; a company certificate whose domains mostly share your domain's name (`example.de`, `example.fr` … for `example.com`) never folds.

In the Certificate view, the CT logs tab shows the SHA-256 of the public key (the data of a TLSA 3 1 1 record), computed locally. **Key continuity**, only when you press **Look this key up in CT**, asks crt.sh for every logged certificate with that key (only the hash is sent; Cert Spotter cannot search by key): the key reused across renewals and since when, or none there (crt.sh's coverage is incomplete, and the page says so). A key carried over renewals keeps TLSA 3 1 1 records and key pins matching until a renewal rotates it; a new key with each certificate needs the next record published 2 × TTL before installing, and a button opens the DANE / TLSA tab. For a CA certificate the wording is for a CA key (TLSA 2 1 1, CA pins).

### CAA restrictions

The Certificate view checks each base domain's CAA records against the certificate's issuer, and reads the RFC 8657 restrictions: `accounturi` (only this ACME account) and `validationmethods` (only these validation methods). It says what they mean for the next renewal, for example "only dns-01 validation is allowed: an HTTP-01 renewal will fail". Domain Health's CAA card lists every issue / issuewild value as usable, restricted (with that renewal note), unsatisfiable or malformed. With expected CAs set in the workspace, the issuer and each CAA value also carry an "Expected CA" or "Unexpected CA" badge.

### Renewal readiness

With 47-day certificates and multi-perspective validation, a renewal that needs a hand fails. `#/renew` checks, per name, what the CA will check: CAA (and its RFC 8657 conditions) against your CA and challenge; the same CAA answer on Cloudflare, Google, DNS.SB and CZ.NIC (a name server that lags behind or fails breaks multi-perspective validation); `_acme-challenge` (a delegation's target, acme-dns, a dangling CNAME a stranger could take over, leftover tokens); DNSSEC; the DNS-01 plugin for the zone's provider (Cloudflare, Route 53, Azure, Google Cloud DNS, DigitalOcean, Hetzner, OVH, GoDaddy, …; Natro, Turhost and İsimtescil have none, so delegate `_acme-challenge`); and the addresses HTTP-01 connects to. A wildcard needs DNS-01, and a wildcard directly under a public suffix (`*.co.uk`, `*.com`) is left out, since no CA issues it. A name whose lookups got no answer in this browser (a rate limit, a dropped connection, one address family unanswered) reads "Could not be checked", never ready. The names can come from a certificate (a file, CT or the sample), which also sets the CA from its issuer; Certificate and SSL Targets link here with the certificate's names. The report has Copy summary, CSV and JSON, and is shareable: `#/renew?names=example.com,*.example.com&ca=letsencrypt&challenge=dns-01`.

The optional **HTTP-01 test** asks Globalping probes in Europe, North America and Asia, over IPv4 and IPv6, for a made-up token under `/.well-known/acme-challenge/` (a 404 is the good answer). An IPv6 address that answers wrongly fails the name; one that refuses or times out while IPv4 passes is a warning with Let's Encrypt, which retries such a connection over IPv4 (other CAs may not). Measurements already paid for are read again for free after a Stop or leaving the view.

### Certificate estate

`#/estate` (Certificates) opens one or more JSON reports of the CLI's `--estate` ([below](#finding-origins-behind-cloudflare-the-cli); one per site or jump host, and any `--json` report works) and shows every certificate your servers serve. Tiles and a filter pick out the expired and expiring ones (< 7 / 30 / 90 days), Cloudflare Origin CA, private CA and self-signed certificates, a name served with different certificates on different endpoints (a load-balancer member or a server the last renewal forgot; the older certificate is marked), one public key in several certificates or on 5 or more addresses, weak keys and signatures (RSA < 2048, SHA-1, MD5), and certificates covering none of the names asked. Each row shows its fingerprints and where it is served; the CSV of the rows shown has the CLI's `--estate --csv` columns, and **Copy summary** names certificates, never an address or a server. With several reports, an endpoint scanned by more than one takes the newest report's answer, and a note says so. The reports are read in the browser, kept only in the tab (a reload, Forget all, another workspace or Delete all local data drops them) and never uploaded; the view works offline.

### MTA-STS policy check

A browser cannot read `https://mta-sts.<domain>/.well-known/mta-sts.txt` itself, so Domain Health's MTA-STS card fetches it on request through one Globalping probe: **Check the policy (1 Globalping probe)**. The page validates it against RFC 8461: version, mode (enforce / testing / none) and max_age; every MX host matched by an `mx` pattern, wildcards included; HTTP 200 without a redirect; served as text/plain, since strict senders ignore any other type; a valid certificate for `mta-sts.<domain>`; and exactly one valid `_mta-sts` TXT record, without which senders never fetch the policy. Each problem comes with fix advice. A failed MX lookup is reported as "not compared", never as "no MX". The probe cannot open SMTP, so the MX hosts' STARTTLS certificates are not checked. The check never changes the score, and **Report (JSON)** includes it as `mtaStsPolicy`.

## Domain overview

`#/domain?name=example.com` builds one page per domain, only when you press **Build overview** (a link or a carried target only fills the box). Seven cards fill as their lookups land, each with an **Open in <tool>** link carrying the name:

- **Registration** (RDAP): registrar, created / expires with a countdown, status flags (a missing `clientTransferProhibited` called out), DNSSEC delegation. For `.tr`, `.de`, `.jp`, `.ch` and other TLDs without RDAP it says so and links the registry's WHOIS.
- **DNS hosting**: the name servers' provider (Cloudflare, Route 53, Azure, Google Cloud DNS, NS1, DigitalOcean, Hetzner, OVH, GoDaddy, Namecheap, Natro, Turhost, İsimtescil, Wix, Squarespace …), the SOA primary and serial, DNSSEC.
- **Mail**: the MX platform (Microsoft 365, Google Workspace, Zoho, Yandex 360, Proton, Mimecast, Proofpoint, Yaani …), SPF and DMARC in one line each.
- **Web**: the apex and `www` behind a CDN, a platform or direct, and HTTPS records.
- **Certificates**: the CAs CAA allows, read as RFC 8659 reads it (no issue property means any CA, issuewild gets its own row, an unknown tag marked critical blocks every CA); on a click, the issuers of the current certificates from one Cert Spotter request, each marked allowed or not by CAA.
- **SaaS verifications**: the services the TXT tokens name (Google, Microsoft 365, Atlassian, Apple, Meta, DocuSign, Stripe, Zoom, Adobe, HubSpot …), never the tokens.
- **Health**: Domain Health's score and worst problems.

A lookup that failed shows "⚠ n/a" with the reason and a Retry that asks only that lookup again. **Copy summary** gives one line per card, and the page prints one card per block.

## Why Global DNS answers differ

Global DNS names the operator of every answer group and uses only the answers already on the page (no extra requests, except one AliDNS question per A / AAAA check on behalf of a US subnet, below) to say why they differ. **Differs by design** means every answer is a CDN / GeoDNS edge and the CNAME chains agree up to the CDN. Names before the CDN may differ when they all lead to the same CDN names, as weighted records do; with no records of the type anywhere (AAAA of an IPv4-only CDN name), only the chains are compared. Otherwise a warning says which part looks like propagation or a misconfiguration: NXDOMAIN or SERVFAIL on some sources, direct addresses next to CDN edges, a CNAME that differs before the CDN, or a move between providers. When only the locations differ it is GeoDNS. A filtering resolver's SafeSearch rewrite is its policy and is not counted as a difference, and SERVFAIL everywhere is shown as an error, never as "agree".

**Mainland China.** The three mainland China locations (Beijing, Shanghai, Guangzhou) are asked through AliDNS's JSON API (its RFC 8484 endpoint sends no CORS header), only for A, AAAA, CNAME and HTTPS, since it cuts larger answers short; they get a row group of their own. Chinese CDNs and WAFs (Alibaba Cloud, Tencent EdgeOne, Huawei Cloud, Wangsu …) are recognised by their CNAME. A CNAME only the mainland China locations get, while every other source agrees, is by design only when AliDNS, asked on behalf of a US subnet, gives the rest of the world's answer — also when every public resolver agrees, as they do for anycast CDNs. When it gives China's answer too, it is an older answer AliDNS still holds and shows as a move between providers. Without that check the title and Copy summary say "most likely" and the text gives the TTL. A CDN only China gets counts only when the last CNAME before its addresses is that CDN's own name.

## Reverse DNS sweep

The **Reverse DNS** view (`#/ptr`, under IP addresses) looks up the PTR record of every address in an IPv4 network up to a /22 (1,024 addresses), a range (`192.0.2.10-192.0.2.50`, also typed with spaces or an en dash), a list of IPv4 / IPv6 addresses, or an AS. For an AS, one RIPEstat request lists its announced prefixes and you pick which to sweep (up to 1,024 addresses together). IPv6 networks are not swept: a /64 holds 2^64 addresses and nothing lists the ones with a PTR record, so only exact IPv6 addresses are looked up.

Each PTR name is forward-confirmed (FCrDNS): confirmed, does not resolve back, no PTR, NXDOMAIN or SERVFAIL. Names under your focus domain are highlighted and listed first. Provider-generated names (`203-0-113-5.isp.example.net`, dynamic / pool / dsl …) fold into one pattern row with a count. Each address shows its operator (CDN, cloud) and the matching server from your inventory. Export CSV, JSON or `names.txt`, hand the names to a Subdomains scan (exact mode), or add the forward-confirmed hosts to Servers as an unsaved draft in your list's own format. The links from the Subdomains › Origins tab (one per IPv4 origin network) and from Domain Health (one per MX address) only fill the form: the sweep starts when you press Sweep.

## Retiring an IP address

The **Retire an IP** view (`#/retire`, under IP addresses) takes addresses or a network up to a /24 (IPv6: a /120) and the domains to check, filled in from your last scan or imported zone (not the zone's own domain when it looks internal, such as `corp.example.com`). For each domain it resolves its own name, the host names this page session knows (the last Subdomains / SSL Targets scan, the imported zone; a domain without any gets a Small-wordlist discovery offered with its query estimate, never run by itself), its MX and NS hosts, its HTTPS record and its SPF policy with every include. It lists every A / AAAA record, CNAME chain, SPF ip4 / ip6 / a / mx mechanism, MX and NS host (an in-zone name server: its glue at the registrar too) and imported zone record (a wildcard is asked through a random name under it), proxied origins included, that still reaches the address, each checked live over DoH.

SPF follows the include path, and the first match of a policy decides: a carve-out such as `-ip4:` in front of a wider range is kept, a term an earlier one shadows is still to be removed, and an `a/24` or `mx/24` that reaches the address only through its CIDR length is to be narrowed; a macro such as `%{i}` reads "cannot tell". The change list is grouped by domain, worst first (breaks mail, breaks DNS, address record, proxy origin, CNAME chain, zone file only, stale), with what to change and the evidence; your server list says which server owns the address. A failed lookup, a stopped check or a domain that does not exist (a typo?) never reads as "nothing points here". **Find other names on the address** asks HackerTarget and ip.thc.org reverse IP, only on a click (the request count and the free quota are written next to the button, and a list cut off after one page is said); their names stay "unverified until checked" until **Check these too**. Export CSV or JSON, or Copy summary.

## DNS change requests and fixes

`#/change` (DNS tools) builds a change request from a template and a form: an ACME DNS-01 TXT record (paste the name your ACME client prints, `_acme-challenge.` included), a CNAME delegation of `_acme-challenge`, Microsoft 365 or Google Workspace mail records, CAA for your CAs (optionally only your ACME account, `accounturi`, and chosen `validationmethods`), an SPF include added or removed, a DMARC step-up, TTLs lowered before a migration, one plain A / AAAA / CNAME / TXT / MX / CAA set, or **Lock down a parked domain** (null MX, `v=spf1 -all`, DMARC `p=reject`, CAA `issue ";"`). Nothing is sent while you type, and the form and every output work offline. Mistakes are listed with the Zone File's wording before anything is written out: a CNAME next to other records, a second SPF record, an SPF record over 10 lookups, a CAA value no CA can satisfy, an ACME token of the wrong shape. The outputs: instructions for the DNS admin in English or Turkish (Add / Replace / Delete / Change the TTL, the name, the values, what goes), BIND, a Route 53 change batch, a Cloudflare API script (it reads `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ZONE_ID` from your shell and never contains a token), octoDNS YAML and Terraform (`cloudflare_record`, `aws_route53_record`). A TXT change is scoped to its kind of record: changing the SPF record never touches the site verifications next to it. The form is in the link (`#/change?t=caa&domain=example.com&cas=letsencrypt`).

**Read the current records** (Ctrl+Enter), only when you click it, asks your DoH resolvers for the names and record types the change touches. The change then keeps what it must keep (the other TXT records next to an SPF record, the whole set a Route 53 UPSERT replaces), removes old values by value and counts the new SPF record's lookups with its includes as they are published now; an edit afterwards asks you to read again. Without a read, each output says what it cannot know instead of guessing, and removing an SPF include is refused.

The **is it live?** link (`#/change/check?z=example.com&r=…`) holds only the zone and the expected records in readable form — the new values and, where they were read, the old ones; at most 20 record sets, 40 values and 4,000 characters. Anyone can open it. It asks Cloudflare, Google, DNS.SB and CZ.NIC from their own browser (names and record types only; nothing is stored on a server) and shows each record on each resolver as done, not yet (no record, still the old value, cached with the old TTL …) or wrong value; a resolver without an answer says why. It checks again with a growing wait (15 s up to 5 min), never before a resolver's cached answer can have expired, and stops — saying which case applies — when everything is done, after two hours, when a long TTL means nothing can change before then, or when a record has had no answer from any resolver for three rounds. **Stop** (Esc) keeps the answers of a round already running; **Check again** asks everything from scratch, so a finished change can be checked again after a revert. **Copy summary** puts the headline and each record set's answers, with this link, on your clipboard.

**Show the fix** in Domain Health and Zone File gives the same outputs for a finding with a concrete fix:

- a missing DMARC record → `p=none` with a report address to create; a DMARC step-up, `pct` or report address → the record with its other tags kept (for a subdomain that inherits its policy, the organizational domain's record);
- SPF `+all` / `?all` / no `all` → `~all`; several SPF records → one merged record; `ptr` and terms after `all` → removed (modifiers such as `exp=` kept);
- no MX → the mail part of the parked lock-down, or advice only when the SPF record shows that the domain sends mail;
- a missing CAA record → one issue value per CA of the domain's current certificates (one Cert Spotter request, only when you click it); a CAA set that refuses the current certificate's CA → that CA added; an unknown CAA tag marked critical → the flag cleared;
- a missing TLS-RPT record → one with a report address.

SPF over 10 lookups gets flattening advice naming the most expensive includes, never an automatic record. The Zone File fixes (a TXT string over 255 bytes re-split, a `localhost` record deleted, CAA flags, a TTL under 60 s, several SPF records) are exact, since they come from the file, and carry no check link. A fix built from a Domain Health report uses a 3600 s TTL and says so, because a public resolver does not tell a zone's own TTL. **Edit in DNS change request** opens the same change in the form.

## Fetching a zone from deSEC or DigitalOcean

Zone File › **Fetch from deSEC or DigitalOcean** reads the zone straight from your DNS provider's API, so there is no export to make: pick the provider, type the zone name and paste an API token. A read-only token is enough, since the page only reads: at deSEC, one whose default policy has no write permission (leave "manage tokens", "create domains" and "delete domains" off); at DigitalOcean, Custom scopes with only `domain:read`. An expiry of a day is enough. The token goes to that provider's API only, in a request header, for that one fetch: it is never saved (not in the browser, not in a workspace) or logged, and its field is emptied as soon as you press **Fetch zone**. A large zone is read in parts (deSEC record type by record type past 500 record sets, DigitalOcean 200 records a page), a provider that asks to slow down is waited for, and **Stop** imports nothing. The listing is then imported like a dropped file, with the zone name confirmed. Cloudflare's API cannot be called from a web page (it sends no CORS header): export that zone and drop the file instead.

## Moving DNS to another provider

Zone File › **New name servers** takes the new provider's name servers (host names or public addresses) and, before you change the NS records at the registrar, asks them for every record set of the imported file through Globalping DNS measurements, with the new server as the resolver: names and types only, internal-looking names skipped by default, proxied records' hidden targets never asked. By default the first server is compared record by record and every other server is asked for its SOA serial. The table lists what is missing, different, not proxied (a proxied record answered with its origin, which becomes public at the switch) or extra there (a parking address, a default MX), and TTL differences; the headline says **fix** (something missing or different, or a server that does not serve the zone yet), **check** (only extra, unproxied, TTL or serial differences left), **partial** (record sets without an answer, a stopped run or more than the 100-probe cap: compare again, or use the CLI) or **ready**. **The move, step by step** says what to do: lower the TTLs (the apex NS too), compare again, handle DNSSEC before the switch (remove the DS at the registrar and wait for its TTL, or pre-publish the new provider's DNSKEY and DS when both support multi-signer, RFC 8901), switch the NS, keep the old zone answering for 48 hours, then check from outside.

[`cli/dns_parity.py`](cli/dns_parity.py) does the same from your machine for zones of any size, for free: every record set (CAA, TLSA and the rest, which Globalping cannot ask), every server, private name servers too. It asks each server directly over UDP / TCP port 53; Python 3.8+, no packages, a file of its own. The tab's **Download the zone (BIND)** gives it any imported format as a BIND file.

```bash
curl -O https://halilibrahimd27.github.io/domainscope/cli/dns_parity.py
python3 dns_parity.py example.com.parity.zone --ns ns1.example.net ns2.example.net
# a server whose name does not resolve yet, asked at its address; a report for scripts
python3 dns_parity.py db.example.com --origin example.com --ns ns1.example.net=192.0.2.53 --json parity.json --fail-on-diff
```

It prints, per server, what is MISSING, DIFFERENT, UNPROXIED or EXTRA, the TTL differences, the SOA serials, the web app's verdict and the order of the move; `--json` / `--csv` write reports. A server whose name does not resolve is reported unreachable and the others are still asked. Exit codes: 0 done, 1 something to fix or a record set without an answer (only with `--fail-on-diff`), 2 usage error, 3 a report not written, 130 interrupted.

Before DNS moves a name to a new server, Retire an IP › **Compare the old and the new server** asks both addresses for the same page (the name as SNI and Host header) from one Globalping probe and shows the answers side by side: status, redirect, content type, title, body hash, HSTS, Server header and the certificate (names, covers the name, trusted, issuer, expiry, fingerprint), with the differences marked. The verdict is same, differs, broken (the new server fails where the old one did not), incomplete or unreachable; a certificate problem both servers share is a warning, not a difference. From inside your network, private addresses included, the CLI does the same:

```bash
python3 ssl_origin_scan.py --compare 10.0.0.5 10.0.0.6 -n www.example.com --path /healthz
```

It opens one TLS connection per address with SNI = the name, sends one GET over it and makes a verifying handshake, then prints both answers side by side, marked ERROR, DIFFERS, WARNING or differs; when neither server answers the verdict is UNREACHABLE (your network may be the cause). `--json FILE` writes both answers; `--fail-on-change` exits with 4 on a broken, different or unreachable result, never for a problem both servers share.

## Comparing and converting zones

Zone File › **Compare** takes a second export of the same zone — the new provider's, or last month's copy — in any format Zone File reads, and compares the two record set by record set, never the text. Names are compared relative to each zone (a copy under another zone name compares too), in any case, with or without the final dot and with escapes decoded; IPv6 written any way, CAA tags in any case, MX / SRV spacing and TXT strings split at other points (byte for byte) count as the same value. The first zone is the starting point: a set is **added** (only in the other zone), **removed** (only in this one), **changed** (other values, a TTL, Cloudflare's proxy flag or a routing policy, values moved between Route 53 set identifiers too) or **the same**. TTL differences, TXT strings split at other points, the SOA serial and timers (and an SOA only one file has) and the NS at the apex (each provider names its own) can be left out, and each row says what an option hid. When the second file does not name its zone, it is read under this zone's name if every name in it fits. A Route 53 change batch is compared as the changes it makes: the record sets it does not touch show as ignored, not removed, and what it deletes as removed. A batch that names routing variants by SetIdentifier is compared only for those variants (the zone's other variants are left alone and the row says so), and a batch that only deletes is compared too. An incomplete export (one page of the Cloudflare API, a truncated Route 53 listing) is flagged above the result and on each set it lacks, and so are problems reading the file. Filter by status, search, export CSV or JSON (proxied records' origin addresses hidden unless you include them) or Copy summary (names and types, never a value).

**Convert** writes the zone for the place it moves to: an RFC 1035 file with `$ORIGIN` and `$TTL` for BIND, Knot, NSD or PowerDNS; a Route 53 change batch (an UPSERT per record set, for `aws route53 change-resource-record-sets --change-batch`), split into several files to send one after another when the zone is larger than one request takes (AWS counts every value and every character of an UPSERT twice: 500 records and 16,000 characters of values per batch); octoDNS YAML that octoDNS 1.22's YamlProvider loads as written (with `escaped_semicolons: true`: TXT values write `;` as `\;`, which the default of octoDNS 2.0 refuses); or DNSControl's `dnsconfig.js`. Nothing is left out without a note: per format, the notes say what it cannot hold or writes differently, with the names concerned — a CNAME at the apex (ALIAS / flattening), TXT over 255 bytes or that is not UTF-8 text, Route 53 aliases (no BIND equivalent), Cloudflare's proxy flag (a comment in BIND, `octodns.cloudflare.proxied`, `CF_PROXY_ON`; Route 53 has none and the origin becomes public), CAA flags and tags, the record types each one has (CAA, SRV, TLSA, HTTPS and SVCB in all four), wildcards, duplicates, routing policies, DNSSEC records, a CNAME that is not alone at its name, and what octoDNS or DNSControl would refuse the whole file over. The BIND, Route 53 and octoDNS files read back into the same record sets, and each format was checked against the tool itself (dnspython, octoDNS, `dnscontrol check`). **Download** or **Copy all**; the file holds the origin addresses too, so share it as you would the export. Both tabs work offline and send nothing.

## DMARC & TLS reports

Receivers such as Google and Microsoft mail a DMARC aggregate report every day to the `rua` address of your DMARC record, and TLS-RPT reports about the TLS sessions to your MX hosts to the `rua` of `_smtp._tls`. **DMARC & TLS reports** (`#/reports`, Mail & domain) reads them with no server: drop the files, a folder or a zipped mailbox export (up to 2,000 files at once). Each file is told apart by its content, not its name; what is neither report, or cannot be read (a damaged or encrypted archive, a report over 32 MB, an archive built to unpack far more than it holds), is listed with its reason. While it reads, a bar counts the reports, those inside an archive too, and **Stop reading** (or Esc) stops between two of them, keeping what was read.

- **Sources.** One row per sending address: volume, DMARC result, SPF and DKIM alignment and the disposition receivers applied. The page looks up the domain's current SPF over your DoH resolvers and asks, for each address, whether it authorizes it, with the 10-lookup and void-lookup limits a receiver applies. Your server list and the SPF decide the class: **your servers**, **authorized third parties** (an include of another organisation, or signing with your DKIM from its own bounce domain), **forwarders** (DKIM passes, SPF does not) and **unknown senders** (spoofing, or a service not set up yet; **Look up** shows their reverse DNS and network). When the SPF record gives receivers a permanent error, the page still says whom it lists, marks the record as the first thing to fix and counts the mail that passed through SPF alone: it fails from now on, and with `p=reject` in force it is refused now.
- **Headline.** DMARC compliance (one decimal, never 100 % unless all mail passed), the policy, and the verdict: not ready for `p=reject`, ready, in force, or in force while mail you send is refused. Up to five sources to fix first, each with what to do: sign with DKIM for the domain, align DKIM or the return-path, add the address to SPF, or repair the SPF record. Notes say when the reports cover less than a week, when `pct` or `t=y` weakens the policy, or when SPF could not be checked.
- **TLS-RPT.** The success rate, the policies senders found (MTA-STS with its mode, DANE, none), the failures by type (`certificate-expired`, `starttls-not-supported`, `sts-policy-fetch-error`, `validation-failure` …) per MX host and sending organisation with advice, and links to Domain Health's MTA-STS card, the TLSA records in DNS Lookup and the MX host's certificate with its DANE tab.
- **Offline**, the reports are still read and classified from their own evidence and your server list; the SPF line says it was not checked, and **Check again** asks once you are online.

The sources export to CSV, and Copy summary names no server of your list. SPF is judged by today's record, not the one in force when a report was made, and telling a DKIM-signing service from a forwarder that kept your signature is a heuristic.

## Domain portfolio and policy audit

**Domain portfolio** (`#/portfolio`, Mail & domain) checks many domains at once, one row each. Paste them (a host name or URL counts as its registrable domain; up to 300) or start from the workspace's recent domains; a shared link only fills the list. Nothing is sent until you press **Check portfolio**: each domain's DNS questions then go to your DoH resolvers, four domains at a time, and its registration lookup to the registry's own RDAP server from the IANA bootstrap, one request at a time per registry with its rate limit waited out (rdap.org only as the fallback, at most one request a second, and left alone for a minute after its own rate limit). A registry that asks for a longer pause, or keeps answering "rate limited", is not asked again until then: its domains say so with the time left, and the other registries' domains go on. The name servers' own domains are looked up the same way, once each however many zones they serve: a name server domain that lapses lets whoever registers it answer for every zone on it, and one the registry does not know at all is flagged first, since anyone can register it today and take over DNS.

- **Columns.** The expiry with a countdown (red under 30 days, amber under 60), the registry status flags (a transfer lock is any transfer prohibition: the registrar's `clientTransferProhibited`, or the registry's `serverTransferProhibited`, shown as "Registry lock"; with neither, the domain is a hijack risk; `serverHold`, `clientHold`, `redemptionPeriod` and `pendingDelete` are critical; a pending transfer is flagged right after them), the registrar, DNSSEC (signed, validated, or broken when the keys cannot be validated), the name servers' domains with their own countdown (or "Not registered"), CAA (the CAs it allows), SPF (valid, lookups of 10), DMARC, DKIM at eight common selectors (optional), MTA-STS and TLS-RPT, and for a domain that takes no mail its lock-down (null MX, `-all`, `p=reject`). A TLD without RDAP (.de, .jp, .tr) gets an honest partial row with its registry's WHOIS link.
- **Working with it.** Rows fill as the lookups land; **Stop** (or Esc) keeps what landed, and the rows not looked up offer **Look up**. A failed lookup is "⚠ n/a" with its reason and a Retry of that cell only. Tiles and a filter pick out what needs a look; every column sorts. Exports: CSV, JSON and **Calendar (.ics)**: one event per expiry, the name servers' domains too, with reminders 30 and 7 days before; importing a newer file updates the events instead of adding new ones.
- **Policy audit.** Each workspace keeps a policy: start from a preset (Baseline, Strict mail, Parked domain), tick rules or edit the JSON, for example `{ "dmarc.policy": ">= quarantine", "dnssec": "signed", "caa": "present", "transferLock": true, "expiryDays": ">= 30" }`. The matrix shows each domain against each rule with its evidence ("12 days left", "CAA also allows sectigo.com"); a rule that could not be checked is "not known", never a pass or a fail. `nsExpiryDays` fails for a name server domain nobody has registered. The policy and the matrix export as JSON and CSV, and the same policy file drives `node tools/ds.mjs audit` ([below](#nightly-checks-without-a-browser-tab-the-headless-runner)).

## Finding origins behind Cloudflare: the CLI

A browser cannot open raw TLS connections to arbitrary IPs. [`cli/ssl_origin_scan.py`](cli/ssl_origin_scan.py) can. It is a single file that needs Python 3.8+ and no extra packages. Run it from a machine inside your network, such as a jump host. It connects to every server IP in your inventory, requests each hostname via SNI, and compares the certificate it gets back with the new one.

```bash
# Download it from the site or the repo
curl -O https://halilibrahimd27.github.io/domainscope/cli/ssl_origin_scan.py

# Renewal day: which servers still serve the old certificate?
python3 ssl_origin_scan.py -t servers.txt --cert new-cert.pem

# Use the names/targets exported from the web app, on ports 443 and 8443
python3 ssl_origin_scan.py -t targets.txt -n names.txt --cert new-cert.pem -p 443,8443

# An inventory with load balancers (backends=, vip=, terminates_tls=no): each server on its own ports, the summary grouped by load balancer
python3 ssl_origin_scan.py -t targets.txt --cert new-cert.pem
# Scan the terminates_tls=no servers too (to see whether a "plain-HTTP" backend answers TLS after all)
python3 ssl_origin_scan.py -t targets.txt --cert new-cert.pem --include-backends

# Renewal week: an RSA + ECDSA pair and another certificate, checked in one run
python3 ssl_origin_scan.py -t targets.txt -n names.txt --cert new-cert-a-rsa.pem --cert new-cert-a-ecdsa.pem --cert new-cert-b-rsa.pem

# Reports for scripts / Excel, and a CI-friendly exit code
python3 ssl_origin_scan.py -t hosts.ini --cert new.pem --json report.json --csv report.csv --fail-on-needs-update

# Internal hosts signed by your own CA are PRIVATE_CERT, not NEEDS_UPDATE; one server listens on 8443 only
python3 ssl_origin_scan.py -t hosts.ini -t 203.0.113.5:8443 --cert new.pem --private-ca internal-ca.pem

# Find the origin of proxied names: sweep a network the Subdomains page suggested
python3 ssl_origin_scan.py -t 203.0.113.0/24 -n shop.example.com api.example.com

# The same sweep, leaving a mail server and a /28 alone (never connected to)
python3 ssl_origin_scan.py -t 203.0.113.0/24 --exclude 203.0.113.25 203.0.113.64/28 -n shop.example.com

# Exact origins from an imported zone file (Zone File › Origins & servers)
python3 ssl_origin_scan.py -t zone-targets.txt -n zone-names.txt

# Every certificate your servers serve, no --cert needed: an inventory with expiry, kinds, conflicts, shared and weak keys
python3 ssl_origin_scan.py -t hosts.ini -n names.txt --estate --json estate.json --csv estate.csv

# Before installing: certificate, chain, key and CSR checked together; fullchain.pem and chain.pem written in server order
python3 ssl_origin_scan.py bundle-check www.example.com.crt ca-bundle.crt private.key -o out/

# A key and its CSR, before ordering the certificate
python3 ssl_origin_scan.py bundle-check private.key request.csr

# Before DNS moves a name to a new server: the old and the new answer side by side (private addresses too)
python3 ssl_origin_scan.py --compare 10.0.0.5 10.0.0.6 -n www.example.com --path /healthz

# Cron: what changed since the last run and certificates expiring within 21 days, posted to
# Slack / Teams / Discord / Telegram / Google Chat (the URL stays out of the shell history)
export DOMAINSCOPE_NOTIFY_URL='https://hooks.slack.com/services/...'
python3 ssl_origin_scan.py -t hosts.ini --cert new.pem --baseline last.json --json last.json --warn-days 21 -q > last.txt
```

It reports one status per server, port and name:

| Status | Meaning |
|---|---|
| `UPDATED` | The server already serves the new certificate. |
| `NEEDS_UPDATE` | The server hosts the name with a different (old) certificate. **Install the new one here.** |
| `ORIGIN_CERT` | The server hosts the name with a Cloudflare Origin CA certificate. Only Cloudflare trusts it, which is right for an origin behind Cloudflare Full (strict) while the name stays proxied. Listed apart, not counted as needing the new certificate. |
| `PRIVATE_CERT` | The server hosts the name with a self-signed certificate, or one issued by a CA you pass with `--private-ca` (usual on internal hosts). Listed apart, not counted as needing the new certificate. |
| `NOT_HOSTED` | The server does not serve this name (it returns its default certificate). |
| `TLS_ERROR` / `TIMEOUT` / `CLOSED` | Unreachable, or the handshake failed. |

`ORIGIN_CERT` and `PRIVATE_CERT` keep the to-do list to the servers that really lag behind; `--strict-public` counts them as `NEEDS_UPDATE` again. `--private-ca FILE` (PEM, DER or P7B, repeatable) takes the CA that signs your internal server certificates; the issuer name and, when both certificates carry one, the key identifier must match. When the new certificate is itself an Origin CA, self-signed or private-CA certificate, older ones of the same kind stay `NEEDS_UPDATE`.

`--cert` can be repeated (an RSA + ECDSA pair, or several certificates renewed together): every file's names are probed, a server serving any of them is `UPDATED`, and the reports name which one (`matches FILE` in the summary, `newCertFile` and `newCertificates[].file` in the JSON, a last `new_cert` column in the CSV). SSL Targets offers one file per certificate (`new-cert-a-rsa.pem`, `new-cert-a-ecdsa.pem`, …) and the matching command. A `--cert` whose names are all in a newer `--cert` with the same key type gets a warning: last year's certificate passed by mistake would make a server still serving it `UPDATED`. With one `--cert` the reports are unchanged.

**Certificate estate.** `--estate` asks every `ip:port` of the inventory without SNI (the default certificate) and for every `-n` name and every host name among the targets, and records each distinct certificate served: fingerprint, subject, names, issuer, expiry, key type and size, public-key SHA-256 and kind (public, Cloudflare Origin CA, private CA, self-signed). The summary lists, most urgent first, the names served with different certificates on different endpoints (OLDER marks the one a renewal left behind), one key in several certificates or on many hosts, weak keys and signatures (RSA < 2048, SHA-1, MD5) and certificates covering none of the names asked, then every certificate by expiry (expired, < 7, < 30, < 90 days, later). The JSON gets an `estate` section and `--csv` writes one row per certificate, endpoint and server. Open the JSON reports in the web app's [Certificate estate](#certificate-estate).

**bundle-check** (the first argument; `--no-color` may come before it) takes certificate, chain, private key and CSR files in any order and format (PEM, DER, P7B; PKCS#1, PKCS#8 and SEC1 keys). It checks that the key belongs to the certificate (the public keys are compared), that the CSR holds the certificate's key and asks for no other names, the chain order (by names and key identifiers; signatures are not verified), a missing intermediate (with the CA's download URL), an extra root and expiry; without a certificate, that the CSR was made with the key. It warns about a certificate marked CA:TRUE or without subjectAltName (what `openssl req -x509` makes by default). An encrypted key is skipped (no password is asked), and no key material is ever printed. `-o DIR` writes `fullchain.pem` (leaf + intermediates) and `chain.pem` when the chain is complete; `--write-haproxy` adds `haproxy.pem` (fullchain + key, owner-only on Linux / macOS, with a warning). Exit codes: 0 every check passed, 1 a check failed, 2 usage error, 3 a file could not be written. `--compare` is described under [Moving DNS to another provider](#moving-dns-to-another-provider).

Targets can be IPs, CIDRs, ranges, hostnames or inventory files, in the same formats the web app accepts. An address or hostname written with a port (`203.0.113.10:8443`, `[2001:db8::10]:8443`, `web01.example.com:8443`, or `web01 203.0.113.10:8443` in a file) is scanned on that port **instead of** `-p`; `-p` applies to every target written without one, and a target listed both ways gets both. IPv6 needs the brackets. A port outside 1–65535 is a usage error on the command line and a warning in a file (JSON values included), never a silently dropped target; so is a hostname with a port next to an address on the same line (write the address with the port). In an Ansible INI inventory — a line under a `[group]` header or with `ansible_*` variables — a port on the host at the start of the line (`203.0.113.10:2222`, `web01.example.com:2222`) is Ansible's SSH port, as Ansible reads it: that host is scanned on `-p`, with a warning, so leave the SSH port there and give the TLS ports with `-p`. One address listed for different servers on different ports is not a duplicate. The Servers view, the `targets.txt` exports and the Verify tab's CLI card keep these ports. `--exclude` takes IPs, CIDRs, ranges or a file of them; it is applied after names are resolved and before any connection. Excluded addresses are listed in the summary, the JSON and the CSV (`EXCLUDED`). Numeric "hostnames" such as `2026092401`, `127.1` or `0x7f.0x1` are refused, because the system resolver would read them as an IPv4 address. Addresses with a leading zero (`010.0.0.1`) are refused too. `0.0.0.0/8`, multicast and broadcast addresses are never scanned. In the `targets.txt` of the Servers view and SSL Targets each server name is one CLI token: spaces, `#`, `;`, `,`, `=`, `/`, `:` and control characters become `_` (`Web Server 1` → `Web_Server_1`) and a name that is an IP address or range is dropped, so the CLI never merges, splits or comments out a server. Exit codes: 0 done, 1 `NEEDS_UPDATE` found (only with `--fail-on-needs-update`; `ORIGIN_CERT` and `PRIVATE_CERT` servers do not trigger it unless `--strict-public` is given), 2 usage error, 3 a report file could not be written after the scan, 4 something changed since `--baseline` (only with `--fail-on-change`), 5 the `--notify` message was not delivered (only with `--fail-on-notify-error`), 130 interrupted. When several apply, 3 comes first, then 5, 4 and 1. Run `python3 ssl_origin_scan.py --help` for everything else.

**Where TLS terminates.** With the [topology keys](#load-balancers-vips-and-nat) in a `-t` file, each server is scanned only on its own ports (an address's own port, else `ports=`, else `-p`), and a server with `terminates_tls=no` is left out unless `--include-backends` is given — except a load balancer passing TLS through with no backend terminating it: TLS would end nowhere, so it is scanned to show what answers there. The summary opens with the servers grouped by load balancer (each load balancer and its backends: install here, re-encrypts, or plain HTTP — no certificate needed), then each VIP with the servers to install on, and the NAT pairs. A `terminates_tls=no` server that answers TLS for your names says the inventory looks wrong instead of "no certificate needed". A VIP or NAT address is not scanned itself: add a VIP with `-t` to see what the active node serves. `backends=` may name a server of another `-t` file. The JSON gets `servers[].topology`, `skippedBackends` and `options.includeBackends`. With `--baseline`, a server newly marked `terminates_tls=no` shows as `SKIPPED`, not as a change, so `--fail-on-change` and `--notify` stay quiet: the inventory changed, not the server.

**Monitoring between visits.** `--baseline previous.json` compares the scan with an earlier `--json` report per IP, port and name: another served certificate, a status that moved (for example `UPDATED` → `NEEDS_UPDATE`, or a new `TLS_ERROR`), and endpoints or names that are new or gone. `--warn-days N` lists the served certificates that expire within N days. `--notify URL`, or `DOMAINSCOPE_NOTIFY_URL`, posts a short summary only when something changed or expires: to a Slack, Microsoft Teams / Power Automate, Discord, Telegram or Google Chat webhook, or as JSON to any other URL. A move from one failure state to another (`CLOSED` → `TIMEOUT`) is listed but does not trigger a message or `--fail-on-change`. The URL is never printed. Give the same file to `--baseline` and `--json` to compare each run with the one before. If a message with changes cannot be delivered, the file keeps the previous report, so the next run reports those changes again.

The origin panel (Subdomains › Origins) and the Behind CDN tab (SSL Targets) write the sweep command for you, for **Linux / macOS** (`python3 …`) or **Windows PowerShell** (`python …`). IPv4 networks go in as the /24 when several origins or one of your inventory servers sit in it. Otherwise they go in as the exact addresses, and so does a /24 in shared cloud / hosting / CDN space that holds none of your servers. IPv6 always goes in as exact addresses (a /48 is far too large to sweep). Addresses you enter under **Exclude addresses** become `--exclude`; a network they cover entirely drops out. They are kept for that scan while you move between pages, and the JSON export's `origin.cliSuggestion` carries the same `--exclude` (POSIX form). A target list too long for one command line is read from `proxied-targets.txt` instead (Verify's CLI card: `verify-targets.txt`), offered as a download next to `names.txt`. The Zone File view uses only the exact origins from the file: addresses and host names, never a /24, with `*.x` names quoted. Every target must be an IP address or network and every name a valid hostname: anything else — for example a hostile name taken from a CT log — is left out and counted, never pasted into the command, and the remaining tokens are quoted for the chosen shell. The Certificate view's `openssl s_client` line follows the same rule: it uses a certificate name only when it passes (a wildcard as `www.<base>`), else `example.com`. Each IPv4 origin network in Subdomains › Origins also links to a [Reverse DNS sweep](#reverse-dns-sweep) of it, which can name hosts the scan did not find.

## Nightly checks without a browser tab: the headless runner

A closed browser tab monitors nothing. [`tools/ds.mjs`](tools/ds.mjs) runs seven of the app's checks under Node 22+ with the app's own libraries (no dependency, no build step): `health` (Domain Health), `subdomains` (discovery, or `--exact` for the names you list), `drift` (a zone export against live DNS), `ct` (current certificates and their issuers in Certificate Transparency), `renew` (renewal readiness), `dane` (the TLSA check of a certificate) and `audit` (the Domain portfolio's policy audit over a list of domains). Each prints a short summary and writes a JSON report (`--json`) and a Markdown summary (`--md`). With `--baseline` it compares the run with the previous report of the same command and opens with "Changes since the baseline": hosts that appear or go, health findings and the score, new certificate issuers or names, zone record sets whose live state moved, renewal verdicts. What a run could not read (a failed lookup, a source that was down that night) is carried into its report from the last run that read it, so the next run compares with that read, never with the gap.

```bash
node tools/ds.mjs health example.com example.org --json health.json --md health.md
node tools/ds.mjs ct --list domains.txt --baseline ct.json --json ct.json --fail-on-change
node tools/ds.mjs audit --policy policy.json domains.txt --json audit.json --md audit.md
node tools/ds.mjs --help
```

Exit codes: 0 done, 1 the run failed, 2 usage error (report files and the baseline are checked before anything is sent), 3 a report could not be written after the run, 4 something changed since `--baseline` (only with `--fail-on-change`) or, for `audit`, a rule of the policy failed (a rule that could not be checked is no failure, unless it failed when last checked), 130 interrupted (nothing written). DNS goes through the app's DoH resolvers with the app's limits (Quad9 and CZ.NIC answer over HTTP/2 only, which Node's fetch does not speak), and nothing goes to Globalping.

[`docs/examples/nightly-domainscope.yml`](docs/examples/nightly-domainscope.yml) runs it every night on GitHub Actions: it commits the reports and keeps one issue open while something changed ([setting it up](docs/examples/README.md)). **Use it in a private repository**, since the results name your hosts, their addresses and your DNS records. **Never commit inventories or zone files unless you mean to.** **No secret is needed**: the workflow's own token commits the results and writes the issue.

## A typical SSL rollout

0. **Subdomains (optional):** see everything first — every name, which are proxied, and the origin networks with a sweep command for your shell, e.g. `python3 ssl_origin_scan.py -t 203.0.113.0/24 -n api.example.com shop.example.com`. If you can export the zone, drop it in **Zone File** instead: you get every name and the exact origin of each proxied record, then **Find certificate targets** or copy the exact sweep command.
1. **SSL Targets:** drop in the new certificate (a lone server certificate gets its missing intermediate and a fullchain.pem; on the server, `ssl_origin_scan.py bundle-check` checks the files the CA sent with your key), confirm the domain, and scan. Your inventory is matched automatically. Renewing several certificates at once (an RSA + ECDSA pair, a few others)? Drop them all, or their folder: they are grouped into sets, one scan covers them, and the **Renewal plan** tab lists which set each server needs, with a CSV work list.
2. **Servers tab:** lists the servers whose DNS points at a covered name. With load balancers in your inventory it says where to install: on both holders of a VIP and on a backend that re-encrypts, never on a plain-HTTP backend — and if DNS points straight at a server the inventory calls plain HTTP, it keeps that server on the list and tells you to check the inventory. **Behind CDN tab:** lists the proxied hosts, their origin hints, and the CLI command.
3. **DANE tab** (if the domain receives mail or uses DANE): press **Check TLSA records**. A record that still pins the old certificate or key is listed with the record to add: publish it, wait 2 × TTL, then install.
4. Install the certificate, then open the **Verify** tab and press **Check from the internet**: every public server is checked for every name it should serve, and "Check again" re-checks only what is not done yet. For private addresses and origins behind a CDN, run the CLI command the tab gives you (`--cert new-cert.pem`; with several certificates one `--cert` per certificate, each offered as a download). Repeat until every server reports `UPDATED`.
5. **Afterwards:** run the CLI with `--estate` from time to time and open its report in **Certificate estate**: a server the renewal forgot shows up as one name served with two certificates.

## Run locally / self-host

No build step and no dependencies. Serve the folder with any static server:

```bash
git clone https://github.com/halilibrahimd27/domainscope.git
cd domainscope
npm run serve            # or: python3 -m http.server 8080 (python on Windows)
```

To host your own copy, fork the repo, enable workflows on the fork's **Actions** tab (GitHub turns them off in new forks) and set **Settings → Pages → Source: GitHub Actions**. Then push to `main`, or run **Deploy to GitHub Pages** once from the Actions tab. The included workflow deploys every push to `main` once CI passes (unit, CLI and offline E2E tests); a red commit is never published. It copies `assets/` under `v/<commit>/` ([`tools/assemble-site.mjs`](tools/assemble-site.mjs)), so browsers never mix cached modules of two deploys, a tab left open across a deploy offers a reload, and the installed app shows "Update ready" (the list of files the service worker keeps offline is written into `sw.js` at deploy time). It also writes `v/<commit>/assets/version.json` (the version, the commit from `GITHUB_SHA` and a digest), which About › What this page sent shows with a link to the commit. Nothing is built; locally the repository is served as it is. The GitHub links in the app point to `REPO_URL` in `assets/js/app.js`; change it in your fork. The weekly intermediate-list rebuild (`.github/workflows/intermediates.yml`) opens a pull request: allow it under Settings → Actions → General → "Allow GitHub Actions to create and approve pull requests", and close and reopen such a pull request before merging it, since one opened with the workflow's token does not start CI.
